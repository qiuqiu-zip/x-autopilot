# Agent 实战系列 · 草稿（AG1–AG30，9/28，未发布）

> 板块二首批。定位：从概念到实战的 Agent 工程系列。
> 核查标记：✅ 共识/已验证 ｜ ⚠️ 需自测或时效内容

### AG1. ⚪ Agent 的解剖：模型 + 工具 + 循环

剥掉所有框架包装，Agent 就是三件套：

**模型**（大脑，负责决策）+ **工具**（手脚，负责执行）+ **循环**（心跳，负责持续工作）。

模型收到任务 → 决定调用哪个工具 → 拿到结果 → 决定下一步 → 循环，直到任务完成。

所有框架（LangGraph/CrewAI/自研）都是这三件套的不同封装。理解了骨架，框架只是方言。

*核查：✅*

### AG2. ⚪ 工具设计第一原则：让 Agent 容易做对

给 Agent 设计工具，第一原则不是功能强大，是**容易用对**：

工具名自解释（search_orders 好过 so2）、参数少而明确（必填参数 ≤3 个）、返回值结构化（JSON + 明确的成功/失败标记）、报错信息可读（Agent 要根据报错自我修正）。

一个反例：把 10 个功能塞进一个工具、参数是个嵌套 JSON——Agent 的调用错误率会翻几倍。

*核查：✅*

### AG3. ⚪ 工具描述 = Agent 的说明书

Agent 选择工具的依据，完全来自你在工具描述里写的话。

差的描述："搜索工具"——Agent 不知道什么时候该用它。
好的描述："搜索历史订单。输入：6 位数字订单号。返回：订单状态和物流信息。当用户询问已购商品的配送或状态时使用；新订单查询不适用。"

**使用场景 + 输入格式 + 返回内容 + 不适用的边界**——四件套写全，Agent 的工具选择准确率直接上一个档。

*核查：✅*

### AG4. ⚪ 函数调用实战：从提示词到结构化输出

Agent 的"调工具"底层是函数调用（Function Calling）：模型输出结构化的 JSON（工具名 + 参数），你的代码执行它，把结果喂回去。

实战细节：用各家原生的 function calling 接口（比自己写提示词解析稳）；参数 schema 定义得越严格（枚举、格式约束），错误率越低；**永远校验模型给的参数再执行**——它偶尔会幻觉出不存在的参数值。

*核查：✅*

### AG5. ⚪ ReAct：思考-行动-观察的循环

最经典的 Agent 模式叫 ReAct，每轮三步：

**思考**（我该干什么）→ **行动**（调用工具）→ **观察**（结果是什么）→ 循环。

它的价值不是流程本身，是**思考过程可见**——你能看到 Agent 为什么这么决策，错了知道错在哪一步。

自己写 Agent，从 ReAct 循环开始就够了，先别碰花哨架构。

*核查：✅*

### AG6. ⚪ 任务拆解：Agent 的规划从哪来

复杂任务（"分析这个季度的销售数据并写报告"）需要 Agent 自己拆步骤。三种来源：

**让它自己拆**（简单任务够用）、**你预拆好步骤**（稳定但僵硬）、**混合**（你给大纲，它填细节）。

实测建议：生产环境用混合模式——**大纲你定，路径它选**。完全放权的 Agent，一半概率跑偏。

*核查：✅*

### AG7. ⚪ 记忆三层：短期、工作、长期

Agent 的记忆分三层，别混：

**短期**：当前对话的上下文（自动有，关了就没）
**工作记忆**：任务执行中的中间状态（变量、文件、TODO 列表——需要你设计）
**长期**：跨会话的记忆（向量库/数据库——需要你建）

最常见的错误：把所有记忆都塞进上下文窗口。窗口是工作台不是仓库——三层各司其职。

*核查：✅*

### AG8. ⚪ 上下文管理：修剪的艺术

Agent 跑久了，上下文被工具结果塞爆。修剪的艺术：

**工具结果摘要化**（1000 字的搜索结果压缩成 100 字要点再进上下文）、**旧轮次归档**（把早期对话移到外部存储，需要时检索）、**关键信息锚定**（任务目标和重要约束每隔几轮重申一次，防"漂移"）。

上下文管理做得好，长任务的稳定性提升一个量级。

*核查：✅*

### AG9. ⚪ 错误处理：重试、降级、兜底

Agent 的错误处理三层：

**重试**（网络抖动类错误，指数退避重试 2-3 次）、**降级**（主工具挂了换备用工具：搜索 API 挂了换另一个搜索引擎）、**兜底**（都不行就如实报告，别硬编结果）。

铁律：**Agent 失败时要说"我失败了，原因是 X"**——编造一个看起来成功的假结果，是 Agent 最危险的失败模式。

*核查：✅*

### AG10. ⚪ 沙箱：Agent 的安全区

Agent 执行代码、操作文件、访问网络——每个能力都是风险面。沙箱原则：

**代码执行**放隔离环境（容器/沙箱，别在主机裸跑）、**文件操作**限定目录（Agent 只能碰指定文件夹）、**网络访问**白名单制、**危险动作**（删除、支付、外发）必须人工确认。

沙箱不是限制 Agent 的能力，是让你敢给它能力。

*核查：✅*

### AG11. ⚪ 成本控制：token 预算制

Agent 跑飞了的另一个代价：token 烧钱。预算制三招：

**任务级预算**（单任务设 token 上限，超了就收束输出）、**工具选择分级**（简单查询用便宜模型，复杂决策用贵的）、**结果缓存**（重复查询走缓存，不重新推理）。

账单翻倍的 Agent，通常不是任务变难了，是循环失控了（见 AG25）。

*核查：✅*

### AG12. ⚪ Human-in-the-loop：审批节点的设计

高风险动作（发帖、付款、删数据）前插入人工审批——设计要点：

**审批点前置声明**（Agent 的计划里写明哪些步骤会请求审批）、**审批内容要完整**（给人类看的是"将要执行什么"，不是"我想执行什么"）、**批量审批的粒度**（同类操作可批量，危险操作逐条）。

我们运营 X 账号的实践：密码和验证码永远人工，发帖内容可批量预审——这就是审批节点的实例。

*核查：✅*

### AG13. ⚪ Agent 评测：任务成功率是唯一硬指标

Agent 的评测比聊天模型更实在：**任务成功率**（给 50 个真实任务，看完成多少）、**平均成本**（每任务 token 消耗）、**平均时长**、**失败模式分类**。

聊天模型可以凭感觉，Agent 必须跑任务清单——因为 Agent 的产出是行动，行动的对错是客观的。

每次改提示词或换模型，重跑任务清单。没有任务清单的 Agent 开发是玄学。

*核查：✅*

### AG14. ⚪ 单 Agent vs 多 Agent：先单后多

"要不要上多 Agent 架构？"——先问三个问题：

任务能拆成**真正独立**的子任务吗？子任务需要**不同工具集**吗？单 Agent 的上下文**装不下**所有工具吗？

三个都是"是"，才考虑多 Agent。否则单 Agent + 好工具 + 好循环，更快、更便宜、更好调试。

*核查：✅*

### AG15. ⚪ 多 Agent 模式一：主管-工人

最常用的多 Agent 模式：一个**主管 Agent** 接任务、拆解、分发；多个**工人 Agent** 各有专长（搜索员、写手、审查员）执行。

设计要点：工人只对自己的子任务负责（上下文干净）、主管做汇总和质量把关、工人之间的通信通过主管中转（别让他们私聊，会失控）。

*核查：✅*

### AG16. ⚪ 多 Agent 模式二：流水线

内容生产类任务适合流水线：**调研 Agent → 写作 Agent → 审核 Agent → 发布 Agent**，每个环节的输出是下一个环节的输入。

设计要点：每个环节定义清晰的输入输出格式（像接口一样）、环节间加质检（不合格打回上游）、流水线的瓶颈环节可以并行多个实例。

我们的账号内容供给，本质就是这条流水线。

*核查：✅*

### AG17. ⚪ 多 Agent 模式三：辩论与评审

高质量决策场景用辩论模式：**多个 Agent 独立作答 → 互相评审对方的方案 → 仲裁者（人或强模型）定稿**。

价值：独立视角能暴露单一 Agent 的盲区。成本：token 消耗是单 Agent 的 3-5 倍。

适用判断：错误代价高的决策（合同、医疗、发布内容）值得辩论；日常任务别浪费。

*核查：✅*

### AG18. ⚪ 框架选择：LangGraph / CrewAI / 自研循环

框架选择的诚实建议：

**自研循环**（AG5 的 ReAct，100 行代码）：学习期和简单任务——没有黑盒，完全可控。
**LangGraph**：复杂状态机和流程控制需求。
**CrewAI**：快速搭多角色协作原型。

反直觉建议：**从自研循环开始**。理解了裸循环，框架才是助力；直接上框架，出了问题你连错在哪一层都找不到。

*核查：✅*

### AG19. ⚪ MCP：Agent 的 USB 接口

MCP（Model Context Protocol）统一了 Agent 连接工具的方式：以前每接一个工具要写一套胶水代码，现在都是标准插座。

对 Agent 工程的意义：工具生态爆发——别人写好的 MCP 服务（搜索、数据库、浏览器），你的 Agent 直接接。

呼应大模型系列 M13 的类比：MCP 统一插头，Marketplace 统一货架。

*核查：✅*

### AG20. ⚪ 案例一：内容运营 Agent（活体案例）

本号的运营就是一个活的 Agent 案例：**扫描目标帖 → 按定位生成回复 → 人工或自动发布 → 记录互动数据 → 反馈优化**。

架构：自研 ReAct 循环 + 真实 UI 通道（绕风控）+ 人工审批节点（内容发布前）。

这就是"Agent 工程"不需要大厂资源的证明：一个循环、几个脚本、一套规则，跑通了完整闭环。

*核查：✅ 本号即案例。*

### AG21. ⚪ 案例二：代码 Agent 的工具集

代码 Agent（如 Claude Code 类）的工具集值得拆解学习：读文件、写文件、执行命令、搜索代码库——**每个工具都对应程序员真实工作的一步**。

可借鉴的设计：工具少而精（6-8 个核心工具覆盖 90% 场景）、执行类工具必须跑在沙箱、给 Agent 看到运行结果的能力（输出回填）。

*核查：✅*

### AG22. ⚪ 案例三：研究 Agent（Deep Research 类）

Deep Research 类 Agent 的流程拆解：**任务理解 → 拆解研究问题 → 多源搜索（迭代）→ 交叉验证 → 结构化报告**。

关键技术：搜索结果的**去重与可信度评分**、研究中途的**子问题修正**（发现新线索时调整方向）、最终报告的**来源标注**。

它的产出之所以可信，是因为每一步都有来源——单靠模型编不出可信的研究。

*核查：✅*

### AG23. ⚪ 案例四：客服 Agent 的边界设计

客服 Agent 的设计重点不是能力，是**边界**：能答什么（产品/流程/状态）、必须转人工什么（投诉/退款纠纷/情绪激动）、绝不做什么（承诺赔偿、透露内部信息）。

边界清单写进系统提示词 + 转人工机制做成工具（Agent 主动调用"转人工"）。

客服 Agent 的事故，90% 是边界设计缺失，不是模型不够聪明。

*核查：✅*

### AG24. ⚪ 案例五：数据分析 Agent 的工具链

数据分析 Agent 的标准工具链：**执行 SQL 的工具 + 读取图表的工具 + 计算工具**。

设计要点：给 Agent 看**表结构文档**（schema 是它的领域知识）、SQL 执行结果回填让它能迭代修正、生成图表作为交付物。

它不会取代数据分析师——它取代的是分析师写 SQL 的时间，分析师的时间转向"问对问题"。

*核查：✅*

### AG25. ⚪ 失败模式一：无限循环

Agent 最经典的翻车：在两个动作之间死循环（搜索→没找到→换个词再搜→还没找到→再搜……）。

防线：**循环次数上限**（硬编码，比如 15 轮必须收束）、**重复检测**（连续两次动作相同就强制换策略）、**预算熔断**（token 超限强制终止并报告）。

三道防线都是几行代码，但没有它们，一次跑飞就是一晚上电费。

*核查：✅*

### AG26. ⚪ 失败模式二：工具滥用

Agent 拿到 10 个工具，会用 2 个解决所有问题——因为那 2 个的描述写得最好。

解法不是删工具，是**描述里写清分工边界**（"X 用于实时数据，Y 用于历史数据"）、**移除任务用不到的工具**（工具越少，选择越准）、**观察调用分布**（某工具从未被调用，要么删掉要么改描述）。

工具集是 Agent 的能力边界，也是它的偏见来源。

*核查：✅*

### AG27. ⚪ 失败模式三：上下文膨胀

长任务跑到一半，Agent 开始"失忆"、重复劳动、答非所问——查上下文，早就被工具结果塞爆了。

防线：AG8 的修剪策略 + **工具结果不入上下文**（大结果写文件，上下文里只留摘要+文件路径）+ **阶段性总结**（每完成一个子任务，生成 3 句话总结替换原始过程）。

上下文是 Agent 的工作台——工作台乱了，什么活都干不好。

*核查：✅*

### AG28. ⚪ Agent 的经济学：成本收益的临界点

Agent 替代人工的经济学账：**单任务成本（token+时长）vs 人工成本 × 频次**。

现状参考：简单研究/整理任务，Agent 成本 $0.1-1，人工 30-60 分钟——划算。复杂创造性任务，Agent 产出需要大量人工修正——不划算。

策略：**从"人工做的最烦的那件事"开始自动化**，那里 ROI 最高。

*核查：✅*

### AG29. ⚪ Agent 的安全边界：攻防已经在发生

Agent 能操作电脑，恶意 Agent 也能——安全议题已经实战化：**提示词注入**（网页里藏指令劫持 Agent）、**数据外泄**（Agent 被诱导发送敏感信息）、**权限滥用**。

防御（呼应 FT214/AG10）：沙箱隔离、权限最小化、关键动作人工确认、来源可信度评估。

你的 Agent 连着你的账号、你的数据、你的钱包——安全设计不是可选项。

*核查：✅*

### AG30. ⚪ 收束：Agent 工程的终极问题是信任

30 篇写完，Agent 工程的核心问题浮出水面：**你愿意把多大的决策权交给它？**

完全信任 = 效率最高 + 风险最大。完全不信 = 安全 + 没用了。

好的 Agent 工程是这个滑块的艺术：**低风险动作全自动，中风险动作抽样审，高风险动作逐条审**——滑块的位置随信任积累动态调整。

我们账号的滑块位置：内容生成自动、发布前人工抽审、身份操作永远人工。这就是当前的最优解，也会随着信任数据的积累慢慢右移。

*核查：✅ 系列收束。*
# Agent 实战系列 · 第二批（AG31–AG40，9/28，未发布）

### AG31. ⚪ Agent 的编排层：从循环到状态机

复杂 Agent 的编排进化：**从 while 循环到状态机**。

状态机把任务定义成明确的状态（理解→检索→起草→自查→完成）+ 状态间的转移条件——每个状态的提示词独立调优，转移条件显式可见。

好处：调试时知道卡在哪个状态、每个状态可独立评测、失败可从任意状态恢复。LangGraph 就是这个思路的产品化。

*核查：✅*

### AG32. ⚪ Agent 的上下文预算表

给 Agent 做预算表（每次任务的上下文分配）：

系统提示词 10% + 任务描述 10% + 少量示例 10% + **工具结果预算 50%**（大头）+ 思考空间 20%。

超预算的处置优先级：压缩旧工具结果 > 砍掉非关键检索 > 升级模型窗口。**预算表让"上下文膨胀"从玄学变成会计。**

*核查：✅*

### AG33. ⚪ Agent 间的交接协议（Handoff）

多 Agent 协作的交接（handoff）协议四要素：**任务摘要**（上游干了什么）、**中间产物**（文件/数据的位置）、**已知问题**（上游发现的坑）、**验收标准**（下游要做到什么程度算好）。

交接差的团队症状：下游 Agent 重复上游的工作、或在上游的坑上继续盖楼。

**交接协议 = Agent 团队的会议纪要。**

*核查：✅*

### AG34. ⚪ Agent 的自我批判（Self-Critique）循环

提升 Agent 质量的性价比之王：**生成后强制自我批判一轮**。

流程：生成答案 → 用批判提示词自查（"找错：事实、逻辑、格式、遗漏"）→ 修订 → 输出。

实测：一轮自我批判能修复 30-50% 的错误，成本只增加一次调用。**批判用同一个模型就有效**——它看自己的输出比看自己的推理更容易发现问题。

*核查：✅*

### AG35. ⚪ Agent 的记忆检索：什么时候翻档案

长期记忆（向量库）的检索时机设计：**不是每轮都检索**。

检索触发器设计：遇到专有名词/历史决策/用户偏好时检索，通用任务不检索。检索太频繁 = 上下文被旧记忆污染 + 成本翻倍。

记忆检索的正确心法：**像人类回忆一样——需要的时候才翻档案，且只翻相关的页。**

*核查：✅*

### AG36. ⚪ Agent 的观察窗口：结果要喂得多细

工具返回结果给 Agent 看，喂多细是个设计决策：

**全文喂**（上下文爆炸但信息全）、**摘要喂**（省上下文但可能丢关键细节）、**分层喂**（先摘要，Agent 要细节时再取全文）。

经验法则：**判断类结果喂全文**（Agent 要自己评估），**事实类结果喂摘要**（Agent 只需要结论）。

*核查：✅*

### AG37. ⚪ Agent 的行为一致性：同一任务跑一百次

Agent 的稳定性测试：**同一任务跑 100 次，统计成功率分布**。

单次成功不代表稳定——Agent 的输出是概率的。100 次跑出 85% 成功率的 Agent，意味着每 7 次任务失败 1 次——这个数据决定它能不能上生产。

**分布思维替代单次思维**，是 Agent 工程师的成熟标志。

*核查：✅*

### AG38. ⚪ Agent 的降级路径设计

每个 Agent 都要有降级路径（degradation path）：

**全功能模式** →（模型超时）→ **简化模式**（减少工具/缩短上下文）→ **兜底模式**（返回部分结果+明确说明未完成部分）。

用户对"部分完成+诚实说明"的容忍度，远高于"全量完成但等 5 分钟"或"直接报错"。

降级不是失败，是设计。

*核查：✅*

### AG39. ⚪ Agent 的可观测性：三根日志柱子

Agent 的可观测性三柱：

**决策日志**（每轮的思考与工具选择——为什么这么干）、**执行日志**（每次调用的输入输出与耗时——干了什么）、**成本日志**（每轮 token 消耗——花了多少）。

三柱合起来的能力：**回放任何一次任务执行的完整过程**——调试、审计、优化全靠它。

*核查：✅*

### AG40. ⚪ 收束：Agent 实战 40 篇的路线图

两批 40 篇收束，给后来者的路线图：

**第 1 周**：AG1-6（骨架：循环+工具+规划）跑通最小 Agent。
**第 2 周**：AG7-12（记忆/错误/沙箱/审批）加上安全与稳健。
**第 3-4 周**：AG25-28（三大失败模式）逐个压测。
**第 5 周**：AG13（任务清单 50 条）建立评测。
**长期**：AG14-17 按需演进多 Agent，AG20 的活体案例持续迭代。

**Agent 工程没有毕业，只有版本迭代。** 系列持续滚动更新。

*核查：✅ 批次收束。*

# Agent 实战系列 · 第三批（AG41–65，9/29，未发布）

### AG41. ⚪ Agent 的幂等性：重试不能变成重复

Agent 重试操作时，"发一条消息"重试三次 = 发三条消息。**幂等性**（同一操作执行多次结果不变）是 Agent 工程的必修课。

实践：写操作带唯一 ID（服务端去重）、先查状态再执行（已做过就跳过）、危险操作记录执行日志。

*核查：✅*

### AG42. ⚪ Agent 的超时分层

不同工具的合理超时不同：搜索 10 秒、API 调用 30 秒、代码执行 5 分钟。**统一超时是设计错误**。

分层配置：快工具短超时快速失败、重工具长超时 + 进度心跳。超时后的行为也要定义：重试？降级？报告？

*核查：✅*

### AG43. ⚪ Agent 的输入清洗

用户输入进 Agent 前的清洗清单：长度截断（防爆上下文）、注入模式扫描（"忽略指令"类）、格式标准化（多余空格/特殊字符）、敏感信息标记。

清洗不是审查用户，是**给模型一个干净的工作面**。

*核查：✅*

### AG44. ⚪ Agent 的输出契约：JSON Schema 实战

让 Agent 输出符合 JSON Schema 的实战要点：schema 里加 description（字段说明影响生成质量）、枚举约束优先于自由文本、required 字段越少越稳、输出后用 schema 校验器验证。

**校验失败的自动重试**（带错误信息重生成）能把格式错误率压到 1% 以下。

*核查：✅*

### AG45. ⚪ Agent 的测试金字塔

Agent 的测试金字塔三层：

**底层（快而多）**：单工具的单元测试（输入→输出正确性）
**中层**：单步任务的集成测试（工具组合）
**顶层（慢而少）**：端到端任务清单（真实场景成功率）

写 Agent 的人 80% 时间花在顶层——正确的比例是倒过来的。

*核查：✅*

### AG46. ⚪ Agent 的回放调试：时间旅行

Agent 跑错了怎么调试？**回放**：保存每次执行的完整轨迹（输入、思考、工具调用、结果），出问题时逐帧回放。

轨迹要记录：每轮的完整上下文快照、每个工具调用的请求响应、每个决策点的模型输出。

轨迹数据还是未来微调的数据源——**调试日志就是训练数据的原材料。**

*核查：✅*

### AG47. ⚪ Agent 的配置外置：别把行为焊死

Agent 的行为参数（提示词、模型选择、工具列表、阈值）全部外置到配置——**改行为不改代码**。

配置版本化 + 灰度切换（10% 流量用新配置）+ 快速回滚——Agent 的迭代速度直接由配置管理决定。

*核查：✅*

### AG48. ⚪ Agent 的多租户：一个系统服务多个用户

Agent 多租户的四个隔离层：**数据隔离**（用户 A 的记忆不能给用户 B）、**配置隔离**（每个用户自己的工具集）、**成本隔离**（用户 B 的重任务不拖垮用户 A）、**权限隔离**（Agent 以用户身份行动，不越权）。

多租户的复杂度集中在"用户上下文切换"——会话状态、记忆、权限的三重隔离。

*核查：✅*

### AG49. ⚪ Agent 的冷启动：新任务怎么接

Agent 接到全新任务类型的处理策略：**任务分类器**先判断（已知模式？相似任务？全新？）→ 已知走缓存路径、相似走模板路径、全新走探索路径（小步试错 + 频繁人工确认）。

冷启动的诚实设计：**承认"我不会"，请求帮助**——比自信跑偏安全一百倍。

*核查：✅*

### AG50. ⚪ Agent 的知识更新：模型不会过期

Agent 依赖的模型有知识截止日期——**用 RAG 补时效、用工具补实时、用定期重训补能力**。

三层更新策略：静态知识进模型（微调）、动态知识进检索（RAG）、实时数据进工具（API）。

**知道每类知识该放哪一层**，是 Agent 架构师的核心技能。

*核查：✅*

### AG51. ⚪ 工具的错误设计：返回什么让 Agent 学会

工具报错的返回设计：**错误信息要可操作**——"错误：无效参数"不如"错误：订单号应为 6 位数字，当前传入 'ABC'"。

Agent 靠错误信息自我修正——**报错写得越好，Agent 自愈能力越强**。这是工具设计里回报率最高的细节。

*核查：✅*

### AG52. ⚪ Agent 的并发控制：同一时间只做一件

Agent 并发执行多个动作的风险：状态竞争、资源冲突、顺序依赖被破坏。

默认策略：**串行执行**（一次一个动作）。确需并发的场景（独立子任务）：明确声明哪些可以并行，其余串行。

并发的收益（快）和风险（乱）之间的权衡，多数场景选稳。

*核查：✅*

### AG53. ⚪ Agent 的成本分层：token 预算制

Agent 任务的成本分层设计：**简单子任务**（分类/提取）用小模型 + 低预算；**复杂决策**（规划/推理）用旗舰模型 + 高预算；**失败重试**有独立预算池。

预算耗尽的处理：优雅收束（输出已完成的部分 + 说明未完成），而不是硬中断。

*核查：✅*

### AG54. ⚪ Agent 的用户反馈闭环

用户对 Agent 结果的反馈（满意/修改/拒绝）是最高价值的训练数据。

产品设计：**让"修改 AI 的输出"成为一键动作**（修改版自动保存为偏好样本）→ 反馈数据定期回流微调/提示词迭代。

反馈闭环没打通的 Agent，永远不会变好。

*核查：✅*

### AG55. ⚪ Agent 的领域适配：通用 vs 专用的选择

通用 Agent 加领域提示词，还是训练领域专用 Agent？判断三问：

**领域词汇量大吗**（大 → 专用微调更稳）、**任务模式固定吗**（固定 → 专用）、**数据够吗**（不够 → 通用 + 提示词）。

数据不足时的务实路线：**通用 Agent + 领域工具集 + 领域 few-shot**——90% 的场景够用。

*核查：✅*

### AG56. ⚪ Agent 的工具版本管理

工具 API 会变（端点升级、参数变更、下线）——Agent 的工具版本管理：

工具声明带版本号、API 变更的兼容层（适配器模式）、工具下线的过渡期（旧工具保留 + 标记 deprecated）、变更的回归测试。

工具链的版本混乱，是 Agent 生产事故的第二大来源（第一是提示词）。

*核查：✅*

### AG57. ⚪ Agent 的任务队列：削峰填谷

Agent 任务量有波峰（用户活跃时段）——**任务队列**削峰：请求先进队列，Agent 按容量逐个处理。

队列的价值：过载时不崩溃只变慢 + 任务可优先级排序（付费用户优先）+ 失败任务可重放。

队列 + 优先级 + 重试策略 = Agent 服务的"交通管理系统"。

*核查：✅*

### AG58. ⚪ Agent 的护栏测试清单

Agent 上线前的护栏测试清单：**越权测试**（Agent 能操作权限外的东西吗）、**注入测试**（外部内容能劫持它吗）、**循环测试**（会不会死循环）、**成本测试**（最坏情况烧多少 token）、**降级测试**（依赖挂了会怎样）。

每项测试一个脚本，每次版本更新全跑——护栏测试的自动化程度 = 上线勇气。

*核查：✅*

### AG59. ⚪ Agent 的文档：给自己和给别人

Agent 系统的文档双轨：**给用户的**（它能干什么、边界在哪、出错怎么办）+ **给开发者的**（架构图、工具清单、配置说明、已知问题）。

文档的更新时机：每次行为变更必更新——**文档过时的 Agent 系统，比没有文档更危险**（误导排查）。

*核查：✅*

### AG60. ⚪ Agent 的伦理配置：什么不做的清单

Agent 系统需要一张"不做清单"：不生成有害内容、不执行危险操作、不泄露隐私、不伪装成人类、不做违法建议——写进系统提示词 + 输出过滤 + 人工审计。

"不做清单"和"能做清单"同样重要——**能力的边界就是产品的责任边界。**

*核查：✅*

### AG61. ⚪ Agent 的迭代节奏：不要天天改

Agent 的迭代纪律：**不要每天改提示词/工具/模型**——变化太频繁，你无法归因效果。

节奏建议：实验期可以频繁试（在测试环境），生产环境按周/双周批量上线（一批改动 + 完整评测）。

**频繁迭代是探索，批量上线是工程**——两个节奏，两套环境。

*核查：✅*

### AG62. ⚪ Agent 的用户教育：管理期望

Agent 产品的用户教育要点：**能干什么**（具体的例子，不是抽象能力）、**不能干什么**（明确的边界，管理期望）、**出错怎么办**（反馈通道、重试建议）。

用户教育做得好的 Agent 产品，投诉率低一半——**用户不怕 AI 不完美，怕的是不知道它不完美。**

*核查：✅*

### AG63. ⚪ Agent 的语言本地化

Agent 面向多语言用户的本地化要点：系统提示词的语言（用目标语言写效果更好）、工具返回的多语言处理、文化适配（称呼/格式/禁忌）、时区与本地格式。

多语言不是翻译——**是每个语言市场独立的提示词工程**。

*核查：✅*

### AG64. ⚪ Agent 的失败案例库：建一个"翻车博物馆"

把 Agent 的每次失败建成案例库：**输入、错误输出、根因分析、修复方案**。

用途：回归测试（修复后不再犯）、新人培训（最好的教材是真实翻车）、模式识别（同类失败归纳出系统性问题）。

**翻车博物馆是 Agent 团队最值钱的内部资产**——它记录的不是失败，是学费。

*核查：✅*

### AG65. ⚪ 收束：Agent 实战 65 篇的知识地图

三批 65 篇的知识地图：

**骨架篇**（AG1-6）：循环、工具、规划
**稳健篇**（AG7-13）：记忆、错误、沙箱、成本、审批、评测
**架构篇**（AG14-19）：单/多 Agent、框架、MCP
**案例篇**（AG20-24）：五个实战案例
**失败篇**（AG25-28）：循环、滥用、膨胀、降级
**深潜篇**（AG31-40）：编排、预算、交接、批判、检索、观察
**工程篇**（AG41-65）：幂等、超时、清洗、契约、测试、回放、配置、多租户……

# Agent 实战系列 · 第四批（AG66–AG90，9/29，未发布）

### AG66. ⚪ Agent 的错误分类学

Agent 的错误分类学（每种错误的处理策略不同）：

**工具选择错误**（选错了工具）→ 改进工具描述 + 加选择引导。**参数错误**（参数格式/值不对）→ 加参数校验 + schema 严格化。**执行错误**（工具本身报错）→ 重试/降级/跳过。**推理错误**（该用 A 工具却用了 B 的思路）→ 加思维链/few-shot。**幻觉错误**（编造不存在的工具或参数）→ 收紧工具列表 + 输出校验。

**错误分类错了，修复就错了**——幻觉不该靠重试修，参数错误不该靠换工具修。

*核查：✅*

### AG67. ⚪ Agent 的提示词分层

Agent 的提示词不是一段话，是分层的：

**L1 身份层**（你是什么 Agent、你的边界）→ **L2 规则层**（行为规范、安全约束）→ **L3 任务层**（当前任务的上下文和目标）→ **L4 状态层**（当前进度、已完成的步骤、剩余任务）。

L1/L2 固定不改，L3 按任务变化，L4 每轮更新——**分层让提示词的可维护性质变。**

*核查：✅*

### AG68. ⚪ Agent 的工具依赖图

Agent 的工具之间有**依赖关系**（工具 B 的输入是工具 A 的输出）——画出依赖图，识别关键路径。

依赖图的用途：**排错时定位是哪条链断了**、**并行时知道哪些工具可以同时调用**、**新工具加入时评估对依赖链的影响**。

没有依赖图的 Agent 调试，是盲人摸象。

*核查：✅*

### AG69. ⚪ Agent 的优雅退出

Agent 的优雅退出（Graceful Exit）三要素：**部分结果**（已完成的部分输出出来，别扔）、**进度说明**（完成了几步/总共几步）、**下一步建议**（用户该怎么继续）。

优雅退出的反面：报错 + 空输出 + 没有任何有用的中间结果。

**退出方式的质量，决定用户是否再给它一次机会。**

*核查：✅*

### AG70. ⚪ Agent 的多轮上下文管理策略

长对话的上下文管理策略选型：

**滑动窗口**（保留最近 N 轮，早期丢弃——简单但有信息损失）、**摘要压缩**（早期对话总结后保留——保留要点但可能丢细节）、**混合**（最近 N 轮全文 + 更早的摘要——平衡但复杂）。

选择标准：**任务对历史信息的依赖程度**。翻译类（需要全上下文）→ 混合；独立问答 → 滑动窗口。

*核查：✅*

### AG71. ⚪ Agent 的提示词温度策略

Agent 的不同步骤用不同的温度（呼应 Prompt 系列 PE40 的 Agent 版）：

**规划步骤**（选择策略）：温度 0.3（要稳定）→ **创意步骤**（内容生成）：温度 0.8 → **格式化步骤**（结构化输出）：温度 0 → **自我批判步骤**：温度 0.5。

**一个 Agent 多步任务 = 温度分层**——这是 Agent 效果优化的隐藏杠杆。

*核查：✅*

### AG72. ⚪ Agent 的异步工具调用

Agent 的耗时工具（搜索、API 调用、代码执行）要异步化：**发起调用 → 继续其他推理 → 结果回来后继续**。

异步的价值：**并行处理多个工具调用**（搜索 3 个来源同时发）、**减少等待时间**。

异步的复杂度：结果回来时的状态管理（上下文怎么合并、顺序怎么保证）——异步只在明确需要时用。

*核查：✅*

### AG73. ⚪ Agent 的工具白名单与黑名单

Agent 的工具权限不是二元的，是分场景的：

**白名单**：明确可以用的工具列表（按任务类型配置）。**黑名单**：明确禁止的工具（如"删除"类工具在只读任务中禁用）。**灰区**：需要人工确认的（"发消息"类——确认后才执行）。

工具权限的粒度：**不是"用不用这个 Agent"，是"这个 Agent 在这个任务里能用哪几个工具"**。

*核查：✅*

### AG74. ⚪ Agent 的自愈设计

Agent 出错后的**自愈设计**（不只是报错，是尝试恢复）：

**重试**（瞬时错误，指数退避）→ **替换**（换个工具做同样的事）→ **降级**（降低目标，完成部分）→ **绕行**（换一条路达到同样目的）→ **报告**（都不行才报告）。

自愈的优先级：**绕行 > 降级 > 替换 > 重试 > 报告**——先绕过去，实在不行再说。

*核查：✅*

### AG75. ⚪ Agent 的成本可视化

Agent 的成本可视化设计（给开发者和用户看的两版）：

**开发者版**：每步的 token 消耗 + 每个工具的调用次数 + 累计成本 → 找出成本黑洞。
**用户版**：任务进度条 + 预计剩余时间 + 简化的用量提示 → 管理预期。

成本可视化的纪律：**每天看**——成本问题发现得越晚，修复越贵。

*核查：✅*

### AG76. ⚪ Agent 的多语言工具调用

Agent 多语言的工具调用挑战：**用户用中文问，工具 API 是英文的**（参数/返回值/错误信息）。

解法：**提示词内做翻译层**（Agent 理解中文问题 → 转成英文工具参数 → 结果翻译回中文回复）。

翻译层的质量 = Agent 多语言体验的上限——**翻译层用模型做，不要用规则做**（规则的覆盖不够）。

*核查：✅*

### AG77. ⚪ Agent 的日志脱敏

Agent 日志的脱敏清单：**用户消息里的 PII**（手机/邮箱/身份证——正则+NER 双抓）、**API 密钥**（工具调用参数里的 key）、**商业敏感**（价格/合同条款）、**模型输出**（也可能包含用户的敏感数据）。

脱敏的时机：**写入日志时立即脱敏**（不要先明文存再脱敏——中间的窗口就是泄露窗口）。

脱敏是合规要求也是用户信任——**日志泄露一次，用户全走。**

*核查：✅*

### AG78. ⚪ Agent 的版本管理：像管代码一样管 Agent

Agent 的版本管理（不只是代码版本）：**提示词版本 + 工具版本 + 模型版本 + 配置版本**——四维版本管理。

版本管理的问题：一个维度的变更会影响其他维度的效果——**四维要联合记录**（每次实验记录全部四维的版本号）。

Agent 版本管理的工具：从简——一个 JSON 文件记录当前版本 + Git 管历史。

*核查：✅*

### AG79. ⚪ Agent 的优雅降级实例：RAG 场景

RAG Agent 的降级实例（从全功能到最简）：

**L4 全功能**：多路召回 + Rerank + 引用 + 流式 → **L3**：向量检索 + 引用 → **L2**：向量检索 + 无引用 → **L1 兜底**：直接用模型知识回答 + 声明"未检索到参考资料"。

每级降级都告知用户（"当前使用简化模式"）——**诚实的降级好过假装正常。**

*核查：✅*

### AG80. ⚪ Agent 的用户偏好学习

Agent 记住用户偏好的设计（个性化）：

**显式偏好**（用户设置的：语言/格式/风格——直接存配置）、**隐式偏好**（用户行为推断的：喜欢长答案/常问某类问题——从交互历史挖掘）。

隐式偏好的挖掘：**"用户修改了 AI 的输出"事件**——修改的方向就是偏好信号（变长了 = 喜欢详细）。

偏好的应用边界：**新会话开始时应用，不要在会话中途偷偷改行为**——那会让用户困惑。

*核查：✅*

### AG81. ⚪ Agent 的工具结果缓存

Agent 的工具结果缓存（省时省钱）：**精确缓存**（完全相同的工具调用直接返回）、**语义缓存**（语义相近的问题返回缓存结果——用 embedding 判断相似度）、**TTL**（缓存过期时间，不同工具不同：天气 5 分钟，文档 1 天）。

缓存的风险：**过时的结果**（数据变了但缓存没更新）——**TTL + 数据版本戳双保险。**

*核查：✅*

### AG82. ⚪ Agent 的测试数据管理

Agent 测试数据的管理要点：**测试集分层**（冒烟测试 10 条 + 回归测试 50 条 + 完整评测 200 条）、**测试数据脱敏**（真实用户数据脱敏后入测试集）、**测试数据版本化**（数据变了测试结果就不可比了）、**新 bad case 自动入测试集**（修复后永远防复发）。

测试数据是 Agent 的"质量资产"——**测试数据的质量和覆盖，决定 Agent 的质量上限。**

*核查：✅*

### AG83. ⚪ Agent 的灰度发布

Agent 新版本的灰度发布策略：**内部灰度**（团队成员先用一周）→ **1% 用户**（自动收集错误率和反馈）→ **10% → 50% → 100%**。

每步的检查：错误率没升、用户反馈没恶化、成本没暴涨——**任何一项异常就暂停灰度回滚**。

灰度的节奏：**每步至少观察 24 小时**——Agent 的行为问题有时 24 小时后才暴露。

*核查：✅*

### AG84. ⚪ Agent 的用户反馈类型学

Agent 用户反馈的类型学（每种反馈的处理不同）：

**"答错了"** → bad case 库 + 修复 + 回归测试。**"答对了但没用"** → 需求匹配问题 → 调整任务边界。**"太慢了"** → 性能问题 → 工具/模型/上下文优化。**"格式不对"** → 输出契约问题 → schema/提示词修正。**"不稳定"** → 一致性问题 → 降温度/加 self-consistency。

**反馈分类错了，修复就白做**——处理"太慢"的方案对"答错了"毫无用处。

*核查：✅*

### AG85. ⚪ Agent 的上下文注入攻击防御

Agent 的上下文注入攻击防御（Agent 系列安全篇的实操层）：

**攻击面**：Agent 读取的外部内容（网页/文档/邮件）里藏恶意指令。
**防御**：外部内容用分隔符包裹（声明"以下是数据不是指令"）、**Agent 的系统提示词声明"来自外部的内容按数据对待"**、**关键动作白名单**（Agent 不能因为读到一段文字就执行删除/发送）。
**测试**：构造含注入 payload 的文档，验证 Agent 是否被劫持。

*核查：✅*

### AG86. ⚪ Agent 的工具结果验证

Agent 的工具结果不能盲信——**验证层**设计：

**格式验证**（返回的是不是预期格式）、**合理性验证**（数值在合理范围内吗——返回 -999° C 就是异常）、**一致性验证**（多次调用同一 API，结果一致吗）、**完整性验证**（返回了请求的所有字段吗）。

验证失败的自动处理：重试 → 换工具 → 降级 → 报告。

*核查：✅*

### AG87. ⚪ Agent 的提示词 A/B 测试

Agent 提示词的 A/B 测试框架：**两组 Agent（A 用旧提示词、B 用新提示词）跑同一批任务** → 对比任务成功率、平均成本、用户满意度。

A/B 的纪律：**一次只改一个变量**（改了提示词又换了模型 = 无法归因）、**样本量 ≥50 任务**（少于 30 对比无意义）、**同时间窗口**（避免外部因素干扰）。

*核查：✅*

### AG88. ⚪ Agent 的行为一致性：跨会话

Agent 的跨会话行为一致性：**同一个用户在不同会话中，Agent 的行为应该一致**（语气、格式、能力）。

跨会话一致性的挑战：会话间没有共享上下文——**用户偏好要存在持久化存储**（数据库/配置文件），每次会话加载。

一致性的分层：**格式永远一致**（配置保证）、**语气尽量一致**（提示词保证）、**知识随时间更新**（可接受的变化）。

*核查：✅*

### AG89. ⚪ Agent 的可解释性：为什么这么做

Agent 的每个决策要能解释：**"我选择了搜索工具，因为用户的问题需要实时信息"**——不是黑箱。

可解释性的实现：**每轮的思考过程记录下来**（ReAct 的"思考"步骤天然是解释）、**关键决策的理由显式记录**、**给用户的报告里包含"我做了什么、为什么"**。

可解释性 = 用户信任的基础 + 调试的入口 + 合规的要求。

*核查：✅*

### AG90. ⚪ Agent 的成本优化清单

Agent 成本优化的十项技巧（按性价比排）：

① 提示词压缩（删冗余）② 小模型路由（简单步骤用便宜模型）③ 工具结果摘要（不全文入上下文）④ 缓存（重复调用直接返回）⑤ 梯度检查点关（推理不需要）⑥ 批量 API（多个请求合并）⑦ 流式输出（提前返回）⑧ 减少重试（指数退避 + 最大重试次数）⑨ Agent 循环上限（防止跑飞）⑩ 定期审计成本（发现异常增长）。

*核查：✅*

# Agent 实战系列 · 第五批（AG91–AG115，9/29，未发布）

### AG91. ⚪ Agent 的工具生态设计：从用到建

Agent 的工具生态三个阶段：**用现成的**（MCP 生态）→ **改现成的**（fork + 定制）→ **建自己的**（独有能力工具化）。

建自己的时机：**内部系统没有现成 Server + 数据敏感不能出域 + 这是你的核心竞争力**。

自建工具的回报率最高，因为别人抄不走。

*核查：✅*

### AG92. ⚪ Agent 的错误恢复策略：五种修复路径

Agent 出错的五种修复路径（优先级从高到低）：**绕行**（换一种方式达到同样目的）→ **降级**（降低目标完成部分）→ **替换**（换一个工具）→ **重试**（可能是暂时性错误）→ **报告**（都不行才报告）。

优先级的原理：**绕行的用户体验最好**（用户看到结果），报告的体验最差（用户看到失败）。

*核查：✅*

### AG93. ⚪ Agent 的上下文工程：不是管理，是设计

上下文管理的进阶：从"管理上下文"（被动修剪）到"**设计上下文**"（主动规划什么信息在什么时候出现）。

设计的三问：这个信息在**哪一步**被需要？**多大**？**影响什么决策**？

设计好的上下文让 Agent 的表现提升一个档——**上下文就是 Agent 的"工作记忆"，工作记忆的质量决定思考质量。**

*核查：✅*

### AG94. ⚪ Agent 的提示词模板系统

Agent 提示词的模板化设计：**固定骨架 + 变量插槽**——

骨架（角色/规则/格式）不变，变量（任务描述/上下文/参数）按需填充。

模板的好处：**新任务的提示词开发从 2 小时到 10 分钟**——只需要填变量。

模板的管理：版本化 + 测试集 + 效果标注——**模板是 Agent 的"配置文件"**。

*核查：✅*

### AG95. ⚪ Agent 的多模型协作：一个任务多个模型

复杂任务的多模型协作：**推理用旗舰，执行用便宜，分类用小模型**——一个任务流水线里三种模型各司其职。

协作的架构：**路由层**（按任务类型分发到不同模型）+ **结果合并层**（多模型的结果统一格式）。

成本收益：**旗舰单干 $1/任务 → 混合 $0.2/任务**——效果差 <10%，成本差 5 倍。

*核查：✅*

### AG96. ⚪ Agent 的安全审计：月度检查清单

Agent 的月度安全审计清单（10 项）：① 提示词注入测试 ② 越权测试（能访问不该访问的吗）③ 循环测试（会死循环吗）④ 成本测试（最坏烧多少）⑤ 泄漏测试（日志里有敏感数据吗）⑥ 降级测试（依赖挂了会怎样）⑦ 并发测试（多请求冲突吗）⑧ 工具测试（每个工具的返回正确吗）⑨ 幻觉测试（编造率多少）⑩ 合规测试（生成内容合规吗）。

每月跑一遍，**每次版本更新也跑一遍**——安全和迭代不冲突。

*核查：✅*

### AG97. ⚪ Agent 的成本追踪：每个任务花多少钱

Agent 的成本追踪设计：**任务级别**（每个任务花了多少 token/多少钱）、**步骤级别**（哪一步花最多——通常是工具调用的结果太长）、**模型级别**（哪个模型花最多）、**时间趋势**（这周比上周贵了还是便宜了）。

成本追踪的发现力：**80% 的成本来自 20% 的任务**——找到那 20%，针对性优化。

*核查：✅*

### AG98. ⚪ Agent 的用户反馈闭环设计

Agent 的用户反馈闭环：**用户使用 → 产生反馈（采纳/修改/拒绝）→ 反馈转化数据 → 数据用于优化 → Agent 变好 → 更多用户**。

闭环的卡点设计：**让"修改 AI 输出"变成一键操作**（用户修改变成训练数据）、**让"拒绝 AI 输出"触发分析**（为什么被拒绝）、**定期向用户汇报改进**（"你上周反馈的问题已修复"）。

*核查：✅*

### AG99. ⚪ Agent 的能力边界测试

Agent 的能力边界测试（知道自己什么能什么不能）：**边界内任务**（应该做对的）、**边界外任务**（应该诚实说做不到的）、**灰色任务**（有时能有时不能——最危险）。

灰色任务的识别：**多次执行，成功率在 30-70% 之间 = 灰色任务**。

灰色任务的处理：降级为人工 + 或加提示词引导 + 或标记为"实验性功能"。

*核查：✅*

### AG100. ⚪ Agent 的部署环境：开发 / 测试 / 生产

Agent 的三环境部署：

**开发环境**（随便试，快速迭代）、**测试环境**（和生产一样的配置，但用测试数据）、**生产环境**（真实用户，真实数据）。

环境分离的纪律：**测试环境的 bug 修完才上生产**、**生产环境的变更必须走灰度**、**三个环境的配置独立管理**。

**环境不分 = 生产事故的源头。**

*核查：✅*

### AG101. ⚪ Agent 的监控告警：不只是"挂了才通知"

Agent 的监控告警不只是"挂了才通知"：**性能告警**（响应时间翻倍）、**质量告警**（成功率下降 10%）、**成本告警**（日 token 消耗翻倍）、**安全告警**（异常访问模式）。

告警的分级：**紧急**（服务不可用 → 立即通知）、**警告**（质量下降 → 当天处理）、**通知**（成本变化 → 每周汇总）。

*核查：✅*

### AG102. ⚪ Agent 的数据管道：从原始数据到训练数据

Agent 产生的数据 → 训练数据的管道：**收集**（交互日志）→ **清洗**（去 PII/去噪/去重）→ **标注**（人工评估质量）→ **入库**（训练数据集）→ **训练**（定期重训）。

管道的自动化：**每一步都有脚本**（人只做审核和批准）——自动化管道让"Agent 变好"从手动变成持续。

*核查：✅*

### AG103. ⚪ Agent 的缓存策略：什么时候缓存

Agent 的缓存策略：**精确缓存**（完全相同的请求直接返回）、**语义缓存**（语义相近的问题返回缓存结果）、**部分缓存**（工具结果缓存，生成不缓存）。

缓存的风险：**过时的缓存**（数据变了但缓存没更新）——**TTL + 数据版本戳双保险。**

*核查：✅*

### AG104. ⚪ Agent 的并发处理：多任务并行

Agent 处理多个并发任务的策略：**任务队列**（先进先出，按顺序处理）→ **优先级队列**（重要任务优先）→ **并行处理**（多实例同时处理）。

并发的风险：**资源竞争**（两个 Agent 同时写同一个文件）——锁机制（文件锁/数据库锁）。

*核查：✅*

### AG105. ⚪ Agent 的测试策略：从冒烟到回归

Agent 的测试策略三层：**冒烟测试**（每次部署后跑 10 个核心 case——快速确认"还能用"）、**回归测试**（每次变更跑 50 个历史 case——确认"没退化"）、**完整评测**（每月跑 200 个 case——全面评估）。

测试的自动化：**CI/CD 集成**（代码提交 → 自动部署到测试环境 → 自动跑测试 → 结果通知）。

*核查：✅*

### AG106. ⚪ Agent 的文档维护：活文档系统

Agent 的文档是**活文档**（自动生成 + 人工维护）：**架构图**（自动生成——代码结构变化自动更新）、**工具清单**（自动生成——从代码中提取）、**配置说明**（人工维护）、**FAQ**（从 issues 中提取）。

活文档的价值：**文档和代码不同步的问题，通过自动生成解决**。

*核查：✅*

### AG107. ⚪ Agent 的迭代管理：变更是有代价的

Agent 的迭代管理：**每次变更（提示词/工具/模型）都是一个"实验"**——

实验的记录：改了什么、为什么改、预期效果、实际效果。实验的管理：**测试环境先试 → 评测通过 → 灰度上线 → 全量**。

迭代的纪律：**每次变更都是一次实验，不是"改一下试试"**——实验有假设、有验证、有结论。

*核查：✅*

### AG108. ⚪ Agent 的工具版本兼容

工具 API 版本更新的兼容策略：**适配器模式**（Agent 和工具之间加一层适配器——API 变了只改适配器）、**版本锁定**（锁定在已知可用的版本）、**兼容性测试**（工具 API 变更后自动跑兼容性测试）。

工具 API 变更的发现：**监控工具的返回格式**（格式变了 = API 可能变了）——变更检测比变更后修复便宜。

*核查：✅*

### AG109. ⚪ Agent 的性能基线：每次优化前先测

Agent 的性能基线：**50 个代表性请求 → 记录 P50/P95 延迟、token 成本、任务成功率 → 这是你的基线**。

基线的用途：**每次改模型/提示词/架构 → 重跑基线 → 对比**。**没有基线的优化是凭感觉。**

*核查：✅*

### AG110. ⚪ Agent 的可靠性工程：不只是"能不能用"

Agent 的可靠性工程（不只是"能不能用"）：**成功率**（任务完成率）、**一致性**（同任务多次的结果一致性）、**可恢复性**（失败后能恢复吗）、**可预测性**（耗时和成本可预估吗）。

四个指标每次版本更新都测——**Agent 的"质量"是四个维度的综合，不只是成功率。**

*核查：✅*

### AG111. ⚪ Agent 的安全实践：从设计到运营

Agent 的安全实践全生命周期：**设计时**（威胁建模/权限最小化/沙箱隔离）、**开发时**（安全编码/依赖审计/注入测试）、**部署时**（灰度/回滚/监控）、**运营时**（月度审计/事件响应/持续红队）。

安全不是阶段——是全生命周期的持续投入。

*核查：✅*

### AG112. ⚪ Agent 的隐私保护：数据不出域

Agent 的隐私保护：**本地模型**（QLoRA + Ollama，数据不出本机）、**数据脱敏**（PII 在进 Agent 前替换）、**本地工具**（文件操作/计算在本地完成）、**网络隔离**（Agent 不访问外网除非必要）。

隐私保护的成本：本地模型的性能比云端旗舰低——**用垂直微调补齐差距。**

*核查：✅*

### AG113. ⚪ Agent 的扩展性设计：从 1 到 100 个用户

Agent 从 1 个用户到 100 个用户的扩展挑战：**并发**（多个请求同时来）、**数据隔离**（每个用户的数据分开）、**成本分配**（每个用户的用量分开计费）、**个性化**（每个用户的 Agent 行为可定制）。

扩展的架构：**无状态 Agent**（Agent 本身不存状态，状态在数据库）→ 多实例水平扩展。

*核查：✅*

### AG114. ⚪ Agent 的维护成本：长期运营的现实

Agent 长期运营的维护成本（诚实版）：**工具 API 变更**（每月 2-5 小时适配）、**模型更新**（新模型出来要重新评测，每月 4-8 小时）、**bug 修复**（每月 2-5 小时）、**用户支持**（每月 5-10 小时）。

**每月 13-28 小时的维护成本**——这是 Agent 产品的真实运营成本。

*核查：⚠️ 具体时间因系统复杂度而异。*

### AG115. ⚪ 收束：Agent 实战 115 篇的终极心法

五批 115 篇收束，终极心法：

**Agent 工程 = 10% 的 AI 能力 + 90% 的工程纪律。**

AI 能力（模型/工具/推理）是骨架，工程纪律（错误处理/安全/成本/测试/监控/文档/版本管理）是血肉。

**骨架人人都有（开源框架一大堆），血肉才是壁垒。**

115 篇的每一篇都在讲血肉的某一根血管——**你的 Agent 活不活得久，取决于你最薄弱的那根血管。**

*核查：✅ 系列收束。*

### AG117. ⚪ Agent 的记忆架构详解

Agent 的记忆架构三层：**短期记忆**（当前对话上下文——窗口有限）、**工作记忆**（任务执行的中间状态——变量/文件/TODO 列表）、**长期记忆**（跨会话的知识和偏好——向量库/数据库）。

*核查：✅*

### AG118. ⚪ Agent 的工具调用链追踪

Agent 的工具调用链追踪（一个请求经过多个工具）：**网关 → Agent → RAG → LLM → 工具 → 结果**——每个环节记录 trace_id → 串联完整链路 → 排查性能瓶颈。

工具：**OpenTelemetry + Jaeger**。

AI 服务的特殊 trace：**LLM 调用作为一个 span**（包含 prompt/response/token 数/耗时）。

**对话管理的核心：不要假设模型记得 10 轮前说的话——重要的事重复说。**

*核查：✅*

持久化的方案：**数据库**（结构化状态）、**文件系统**（非结构化数据）、**向量库**（语义检索）。

*核查：✅*

## 二季 · 翻车与救火篇（AG131–145，10/1）

### AG131. ⚪ 翻车实录：一晚上烧穿 API 账单的死循环

Agent 把"搜索→失败→重试"跑了一整晚，早上账单提醒才被发现。

根因：重试没有上限，失败没有升级路径。

两个必加的闸：单任务重试上限（3 次封顶）+ 单日成本熔断（超了就停）。

Agent 的自主性和你的钱包之间，必须有一个硬编码的边界。

### AG132. ⚪ 工具参数幻觉：模型会编造不存在的参数

Agent 调 API 时用了一个文档里根本不存在的参数——它自己"发明"的。

防法三条：工具 schema 写死必填字段、服务端拒绝未知参数（而不是忽略）、报错原文喂回给模型让它自己修。

最忌讳静默忽略：错误参数被吞掉，Agent 以为成功了，你拿到一堆脏数据。

### AG133. ⚪ 翻车实录：把测试库当生产库清了

配置里一个环境变量的差异，Agent 在生产库跑了为测试环境写的清理脚本。

教训：Agent 的权限要跟环境绑定，而不是跟任务绑定。

生产环境只发只读凭证，写操作走人工确认队列——这不是效率问题，是生存问题。

### AG134. ⚪ 重试的三层设计：工具级、任务级、流程级

大多数人只想到第一层：工具调用失败重试 3 次。

任务级：子目标卡住要换策略，而不是换个姿势继续撞墙。

流程级：整个任务跑偏要有回炉机制——已完成的部分留住，失败的部分重规划。

三层都有的 Agent，才配叫健壮。

### AG135. ⚪ 犹豫检测：什么时候把方向盘交还给人

Agent 最危险的不是失败，是自信地走向悬崖。

给 Agent 加犹豫检测：连续两次工具失败、置信度低于阈值、操作不可逆（删除/转账/外发）——任意触发，立即停下问人。

会喊救命的 Agent 才是好 Agent。

### AG136. ⚪ 上下文塞爆之后的三个降级方案

上下文满了，硬截断是最差的选择。

方案一：滚动摘要——旧对话压成要点保留；

方案二：外置记忆——关键事实写进向量库，用时检索回来；

方案三：任务拆分——大任务切成独立子任务，各自带干净上下文。

上下文是稀缺资源，管理它的水平就是 Agent 工程的水平。

### AG137. ⚪ Agent 日志怎么记，才能事后复盘

print 日志救不了 Agent。复盘需要结构化 trace：每次模型调用（输入摘要/输出摘要/token 数）、每次工具调用（参数/结果/耗时）、每个决策点（为什么选这条路）。

一个意外的好处：trace 数据本身就是最好的评测集和微调素材。

日志做得好，你的 Agent 每天都在自我改进。

### AG138. ⚪ 一个 Agent 还是多个：拆分的真实判据

不是"任务大就拆"。真实判据两条：

一、上下文冲突——两个子任务的上下文互相污染（比如"写代码"和"查合规规范"）；

二、权限差异——一个要只读一个要写，权限必须隔离。

满足任一条才拆。为了架构好看强拆多 Agent，只会收获一堆通信 bug。

### AG139. ⚪ Agent 间通信：消息传递优于共享状态

多 Agent 协作的第一坑：让它们共享一块状态区，结果互相覆盖对方的数据。

消息传递（A 干完把结果发给 B）慢一点，但因果关系清晰、可追溯。

共享状态只适合一种东西：所有人都只读的事实数据。

协作历史，永远走消息。

### AG140. ⚪ 长任务 Agent 的断点续跑

跑了 40 分钟的任务挂了，从头再来？没人受得了。

断点续跑的核心：把任务状态持久化成检查点——已完成步骤的输出、当前计划、剩余步骤。

恢复时读检查点接着跑，而不是重新理解整个任务。

长任务的体验差距，全在这一处。

### AG141. ⚪ Agent 的金丝雀发布：先放 5% 流量

Agent 上线别全量。先放 5% 流量，盯三个数：任务成功率、人工介入率、单任务成本。

三项稳住一周，再翻倍放量。

回滚预案要一键可用——Agent 出问题的影响是"错误地做完了事"，比"没做事"难收拾得多。

发布纪律这东西，Agent 时代一条都不能少。

### AG142. ⚪ 工具接口设计：让模型不容易用错

三条约定，砍掉一半调用错误：

一、参数用枚举别用自由文本——能选的列出来，别让它编；

二、返回值带"下一步建议"——模型看着提示走，不容易迷路；

三、危险操作单独拆接口——调用它本身就是明确的意图信号，方便加确认。

工具是给模型用的 UI。UX 做得好，模型就聪明。

### AG143. ⚪ Agent 评测：用任务成功率回答"好不好"

"回答质量"评不了 Agent。该评的是任务级指标：完成率（多少任务没要人工就跑完）、正确率（跑完的里多少是对的）、成本、时长。

先拿 20 个真实任务建评测集，每次改 prompt 或换模型就全量重跑。

数字不动，说明你的"优化"是自我安慰。

### AG144. ⚪ 成本归因：一次任务到底花在哪

"这个月 Agent 账单涨了 3 倍"——哪里涨的？多数团队答不上来。

归因要细到：哪个环节调用最多、哪个环节上下文最长、哪些是可以缓存的重复调用。

优化顺序永远是：砍重复调用 → 压上下文 → 换便宜模型。

顺序错了，越优化越贵。

### AG145. ⚪ 收束：从 demo 到生产，Agent 要过 10 道门

二季收束。从能跑的 demo 到敢托付的生产系统，中间是十道门：

重试上限、成本熔断、权限绑定、犹豫检测、结构化 trace、任务级评测、金丝雀、断点续跑、工具防呆、成本归因。

每道门都不难，难的是 demo 跑通之后，你还愿意一道一道过。

愿意过的团队，就是两年后的"别人家的 Agent"。
