# RAG 全链路系列 · 草稿（RG1–RG20，9/28，未发布）

### RG1. ⚪ RAG 三步流程：检索、增强、生成

RAG（检索增强生成）三步：**你的问题 → 从知识库里找出最相关的几段资料 → 连同问题一起交给大模型回答。**

它解决两个致命问题：模型不知道你的私有数据、模型的知识有截止日期。

一句话记住：**RAG 是开卷考试——模型还是那个模型，但给它发了参考资料。**

*核查：✅*

### RG2. ⚪ 什么时候用 RAG：两个判断

两个判断，全中就用 RAG：**知识会变吗**（价格、政策、文档——会变的进知识库，别指望微调记住）、**知识是你的吗**（企业内部文档、个人笔记——模型天生不知道）。

都不中（纯创作、通用常识）→ 不需要 RAG，直接问。

*核查：✅*

### RG3. ⚪ RAG 效果差，七成问题在检索

RAG 效果差，多数人去改提示词——方向错了。

业界经验：**RAG 的失败七成在检索**（没找对资料），三成才在生成。找错了资料，模型拿着错误依据认真胡说。

所以调优顺序：先修检索（分块、embedding、rerank），再修生成（提示词）。本系列 20 篇的编排就按这个比例。

*核查：⚠️ 比例为经验归纳，非严格统计。常青。*

### RG4. ⚪ 文档分块：按语义切，不按字数切

知识库建的第一步是把文档切成小块。最大的坑：**按固定字数硬切**——把一段完整的话从中间腰斩。

正确姿势：**按语义切**（按段落/章节/主题边界）、块间保留 10-15% 重叠（防断章取义）、表格和代码块整块保留不切。

分块的质量决定检索的上限——切烂了的文档，后面神仙也检索不好。

*核查：✅*

### RG5. ⚪ 分块大小：没有标准答案，有测试方法

块多大合适？300 字、500 字还是 1000 字？**没有标准答案，只有测试方法**：

用你的真实问题集，测 3 种块大小（比如 256/512/1024），看检索命中率哪个高。

经验范围：问答场景 300-500 字、文档摘要场景 1000-2000 字。你的数据你说了算。

*核查：✅*

### RG6. ⚪ Embedding 模型选型：三个实测维度

选 embedding 模型（把文字变向量的模型）看三个实测：**中文效果**（用你的真实问题测命中率）、**速度**（百万级文档的入库时间）、**维度**（维度越高存储越贵）。

别只看 MTEB 榜单——**用你的数据实测**，结果经常和榜单不一致。开源的 BGE 系列是中文场景的常见起点。

*核查：✅*

### RG7. ⚪ 向量数据库选型：从简开始

向量数据库的选型焦虑可以治好：**数据量小于百万级，先用最简单的**。

入门：Chroma / FAISS（本地、免费、几行代码）
生产：Milvus / Qdrant / pgvector（Postgres 插件——已有 PG 的团队零成本新增）

先跑起来，数据量真上去了再换。**迁移的成本，低于一开始就上重装备的成本。**

*核查：✅*

### RG8. ⚪ 检索策略：向量、关键词、混合

三种检索方式各有盲区：

**向量检索**：懂语义，但精确匹配弱（搜"错误码 0x80070005"可能搜不到）
**关键词检索**：精确匹配强，但不懂同义词
**混合检索**：两者都跑，结果融合（RRF 重排序）——生产标配

技术文档、代码、错误码类知识库，混合检索是必选项。

*核查：✅*

### RG9. ⚪ top_k：给模型几条参考资料

检索出 top_k 条资料给模型，k 怎么选？

太小（k=1-3）：漏掉关键信息的风险大。太大（k=20）：噪音淹没重点，token 也贵。

经验起点：**k=5 + Reranker 精排**。配合"资料相关性分数过滤"（低于阈值的丢弃），宁可少而准，不要多而杂。

*核查：✅*

### RG10. ⚪ Reranker：检索精排的一 smaller 步

向量检索是"粗排"（快但糙），**Reranker 是"精排"**（慢但准）：用交叉编码器逐条细算问题和文档的相关性。

流程：向量检索 top 20 → Reranker 精排 → 取 top 5 给模型。

多花几百毫秒，命中率提升显著——RAG 提效清单里性价比最高的一个组件。

*核查：✅*

### RG11. ⚪ 查询改写：用户的问法 ≠ 检索的问法

用户问"这个东西多少钱"——知识库里写的是"产品定价策略"。字面不匹配，检索就 miss。

解法：**查询改写**——用 LLM 把用户口语改写成检索友好的表达（提取关键词、扩展同义词、拆解复杂问题）。

这一步加上后，检索命中率普遍提升 20-40%。RAG 里最被低估的组件。

*核查：⚠️ 提升数字为实践观察。常青。*

### RG12. ⚪ 多轮对话检索：先把指代说清楚

多轮对话的 RAG 有个特有问题：用户第二句问"那它多少钱呢？"——"它"是谁？

解法：**查询改写先做指代消解**（结合对话历史，把"它"还原成具体对象，再拿去检索）。

不做这步，多轮对话的 RAG 基本不可用——检索拿到的是"那它多少钱呢"这种废查询。

*核查：✅*

### RG13. ⚪ 结构化数据的 RAG：表格走 SQL 路线

知识库里大量内容是表格（价格表、规格表、统计报表）？向量检索对表格效果差。

解法：**表格走 SQL 路线**——用 Text-to-SQL 把自然语言变成查询，精准取数。

混合知识库的正确架构：文档走向量检索，表格走 SQL，路由层判断问题该走哪条路。

*核查：✅*

### RG14. ⚪ RAG 评测：两个必须盯的指标

RAG 评测盯两个指标：**检索命中率**（正确资料有没有被找回来）、**回答忠实度**（回答是否忠于检索到的资料，有没有自由发挥）。

工具：RAGAS 一类框架自动评测。没有这两个指标的 RAG，效果好坏全靠体感——体感是靠不住的。

*核查：✅*

### RG15. ⚪ 幻觉治理：回答必须带引用

RAG 治幻觉的最后一道防线：**回答必须标注引用来源**（"根据《XX 文档》第 3 节……"）。

实现：提示词强制要求 + 生成后校验（回答里的关键论断能在检索资料里找到对应）+ 找不到就回"资料中未找到"。

带引用的 RAG，用户敢用；不带引用的 RAG，用户用一次就走了。

*核查：✅*

### RG16. ⚪ 数据更新管道：知识库的新鲜度

知识库的致命伤是过时：上周的价格、旧版的政策。数据更新管道三问：

**更新频率**（每天/每周同步？）、**更新方式**（全量重建还是增量入）、**删除机制**（作废的文档有没有从库里删掉）。

"加了新文档忘了删旧文档"是 RAG 回答自相矛盾的头号原因。

*核查：✅*

### RG17. ⚪ 权限过滤：谁能检索什么

企业 RAG 的必备能力：**权限过滤**——财务部的人检索不到 HR 的薪酬文档。

实现：文档入库时打权限标签，检索时按用户身份过滤（在向量检索的过滤条件里，不是检索完再删）。

权限做在检索后而不是检索时，是安全事故的常见来源——检索本身就会把内容送进模型上下文。

*核查：✅*

### RG18. ⚪ 成本优化：缓存与路由

RAG 的成本优化三板斧：**缓存**（高频相同问题直接返回缓存答案）、**路由**（简单问题用小模型，复杂问题才上大模型）、**精简上下文**（Reranker 后只给 3-5 条最相关的，别把 20 条全塞进去）。

三板斧下来，成本通常能砍 60-80%，效果不掉。

*核查：✅*

### RG19. ⚪ 为什么你的 RAG 像人工智障：失败案例复盘

典型的"人工智障 RAG"复盘：用户问"退货流程"，系统检索到"退货保险产品介绍"（向量相似但语义完全不同）→ 模型拿着错误资料一本正经回答。

病灶三连：文档切分切烂了 + 没有查询改写 + 没有 Reranker。

对照本系列 RG4/RG11/RG10 逐个修——修完的系统和修之前的，是两个产品。

*核查：✅*

### RG20. ⚪ 进阶路线：从朴素 RAG 到 Agentic RAG

朴素 RAG 之上还有三条进阶路线：

**HyDE**（让模型先生成假设答案，再用它去检索——以答找文）、**GraphRAG**（知识图谱结构化，擅长多跳关系问题）、**Agentic RAG**（让 Agent 决定：要不要检索、检索什么、检索几轮、够不够回答）。

路线选择：朴素 RAG 覆盖 80% 场景，先跑通朴素版，遇到真实瓶颈再上进阶——**别用架构炫技替代问题解决。**

*核查：✅*
