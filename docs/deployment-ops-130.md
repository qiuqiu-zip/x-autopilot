# 部署运维系列 · 草稿（DM1–DM20，9/28，未发布）

> 板块二：把"跑通的 demo"变成"稳定的线上服务"。对象：微调/RAG/Agent 做完之后的上线与运维。
> 核查标记：✅ 运维共识 ｜ ⚠️ 时效内容

### DM1. ⚪ 部署形态总览：三种位置，三种代价

LLM 应用的三种部署位置，代价完全不同：

**云 API**（零运维、按量付费、数据出域）、**自建 GPU**（数据不出域、固定成本、运维自理）、**边缘设备**（离线可用、性能受限）。

选型一句话：数据敏感 → 自建；量小 → API；离线刚需 → 边缘。**先定位置，再谈其他。**

*核查：✅*

### DM2. ⚪ 容器化：Docker 是部署的地基

微调模型服务的容器化最小集：基础镜像（CUDA + PyTorch）、模型权重挂载（不打进镜像，体积爆炸）、推理服务（vLLM/Ollama）、健康检查端点。

一条铁律：**配置和权重外置**——镜像只含代码，改配置不用重 build。

*核查：✅*

### DM3. ⚪ GPU 资源规划：从 token 吞吐反推

买多大的卡？从业务反推：**日均调用量 → 峰值 QPS → 单卡 token 吞吐 → 需要几张卡**。

例：日均 10 万次对话 × 平均 500 token/次 = 5000 万 token/天 ≈ 峰值 1500 token/秒 ≈ 一张 4090 跑 7B 量化模型刚好。

再加 30% 余量。**先算再买，别反过来。**

*核查：✅ 计算方法通用，数字随模型浮动。*

### DM4. ⚪ 推理服务选型：vLLM / TGI / Ollama

三个推理服务器的定位：

**vLLM**：生产首选（吞吐最高、OpenAI 兼容 API、多模型服务）
**TGI**：HuggingFace 官方，生态稳
**Ollama**：本地/开发用，生产并发弱

生产用 vLLM，本地玩用 Ollama，中间地带才考虑 TGI。

*核查：✅*

### DM5. ⚪ 流式输出：用户体验的分水岭

流式输出（SSE 打字机效果）的实现要点：推理服务支持 stream 模式、前端逐 token 渲染、**首字延迟**是核心指标（从请求到第一个字的时长）。

非流式的回答哪怕总耗时 5 秒，体感也远差于流式的"1 秒出首字 + 持续输出"。

流式不是锦上添花，是 LLM 产品的及格线。

*核查：✅*

### DM6. ⚪ 并发与限流：别让一个用户打死服务

并发保护的标配三件：**并发上限**（同时处理的请求数，按 GPU 容量设）、**用户级限流**（单用户每分钟 N 次，防刷）、**排队机制**（超出的请求排队而不是拒绝，给用户预期）。

LLM 推理的并发成本是传统 API 的十倍以上——每个请求都占着 GPU 算几秒。不做限流的服务，第一个大客户就能把它打死。

*核查：✅*

### DM7. ⚪ 监控三件套实操

落地监控三件套的最小方案：

**指标**：QPS、首字延迟 P50/P95、token 吞吐、错误率——Prometheus + Grafana
**日志**：每次请求的 prompt/response/耗时/用户——脱敏后落库
**告警**：错误率 >5%、P95 延迟翻倍、GPU 利用率异常——发到值班群

三件套一天能搭完，但没有它的生产服务就是裸奔。

*核查：✅*

### DM8. ⚪ 日志与追踪：出了问题能回放

LLM 服务的日志特殊性：**每次请求都是一次"模型行为记录"**——输入、输出、模型版本、检索内容（RAG 场景）、耗时。

价值：用户投诉"答错了"→ 能回放当时的完整输入输出 → 定位是检索没找到还是模型胡说。

日志脱敏（PII）和保留期限（合规）要在设计时定好，事后补很难。

*核查：✅*

### DM9. ⚪ 成本监控与预算告警

LLM 服务的成本会自己长大：token 用量 × 单价 × 用户增长。三道防线：

**用量看板**（每天 token 消耗和成本，按用户/功能拆分）、**预算告警**（日成本超阈值就通知）、**硬熔断**（单用户消耗超限自动限流）。

云 API 的账单刺客和自建的电费刺客，都要用看板关住。

*核查：✅*

### DM10. ⚪ 灰度发布与回滚

新模型/新提示词上线的灰度三步：**1% 流量**（内部用户先用）→ **10%**（观察指标一天）→ **全量**。

回滚预案：旧版本模型和配置**永远保留热备**，切换做成配置开关（秒级生效），回滚不重新部署。

模型的灰度比传统软件更重要——它的"bug"是行为变化，肉眼难发现，只能靠指标。

*核查：✅*

### DM11. ⚪ 多模型路由网关

多个模型（自建微调 + 云 API + 不同尺寸） behind 一个网关：**路由层**按任务类型、成本预算、可用性分发请求。

路由规则示例：简单分类 → 本地 7B；复杂推理 → 云端旗舰；自建服务超时 → 自动 fallback 到 API。

网关还统一了日志和计费——多模型的复杂度，全部关在网关这一层。

*核查：✅*

### DM12. ⚪ 提示词的线上热更新

提示词改版不想重启服务？**提示词外置化**：提示词存数据库/配置中心（带版本号），服务启动时拉取，更新时推新版本。

配合灰度（PE20 的 A/B）：10% 用户用新提示词，指标对比后全量。

提示词是 LLM 应用里**变更最频繁的部分**——热更新能力直接决定迭代速度。

*核查：✅*

### DM13. ⚪ 数据管道运维：知识库的新鲜度保障

RAG 知识库的运维管道：**文档源监控**（源有更新就触发入库）、**入库任务幂等**（重复入库不产生重复数据）、**失败重试与告警**（入库失败要有通知，别让知识库悄悄过时）。

知识库的"最后更新时间"要显示给用户——过时的知识库不如没有知识库。

*核查：✅*

### DM14. ⚪ 向量库运维：备份与重建

向量库的运维三件事：**备份**（定期快照，或保证可从源数据全量重建）、**重建演练**（换 embedding 模型 = 全量重建，流程要提前演练过）、**性能监控**（查询延迟随数据量增长的变化）。

重建演练特别重要：换 embedding 模型的决定很常见，但"百万级文档重新入库要多久"很多人没算过。

*核查：✅*

### DM15. ⚪ 安全加固：密钥、审计、注入防御

LLM 服务安全加固三件：**密钥管理**（API key 进密钥管理服务，不进代码和环境变量明文）、**审计日志**（谁在什么时候用了什么模型处理了什么——企业客户必问）、**注入防御**（用户输入的提示词注入检测，呼应 PE17）。

企业客户的采购评审里，这三项是必答题。

*核查：✅*

### DM16. ⚪ 高可用：挂了怎么办

LLM 服务的高可用设计：**多实例**（无状态服务，挂一个顶上）、**模型双版本热备**（新旧权重都在显存里，秒切）、**fallback 链**（自建模型超时 → 云 API 兜底 → 优雅降级文案）。

最不体面的故障：用户看到"服务器错误"。最体面的故障：回答变慢 + 提示"当前使用备用模型"。

*核查：✅*

### DM17. ⚪ 升级策略：模型和框架的版本管理

模型升级的版本管理：新模型先过评测流水线（FT119）→ 灰度（DM10）→ 全量。**框架升级**（vLLM/PyTorch 大版本）：在影子环境跑一周再切。

两个坑：模型升级可能改变输出风格（用户感知得到）；框架升级可能改变性能基线（监控对比升级前后）。

升级的唯一安全姿势：评测 + 灰度 + 可回滚，三件套齐了再动。

*核查：✅*

### DM18. ⚪ 故障演练：在真故障之前

故障演练的三个场景，每季度跑一遍：**GPU 全挂**（fallback 链生效吗）、**知识库过时**（监控会告警吗）、**流量翻倍**（限流和扩容预案跟得上吗）。

演练的成本是半天，真故障的代价是用户流失。

没演练过的故障预案，等于没有预案。

*核查：✅*

### DM19. ⚪ SLA 设计：对用户的承诺怎么说

LLM 服务的 SLA 设计要点：**承诺要留余量**（内部做到 P95 3 秒，对外承诺 5 秒）、**降级条款**（高峰期降级到备用模型算不算违约，写清楚）、**免责边界**（模型输出的事实准确性——目前行业的普遍做法是不承诺）。

对用户诚实的 SLA，好过对销售负责的 SLA。

*核查：✅*

### DM20. ⚪ 收束：小团队的最小运维

小团队的最小运维清单（一人兼职也能跑）：

容器化部署（DM2）+ 监控三件套（DM7）+ 灰度回滚（DM10）+ 每日成本看板（DM9）。

其余的高可用、多库路由、故障演练——**业务长大再说**。

运维的原则和微调一样：**先跑起来，按真实故障逐步加固。** 系列收束。

*核查：✅*

# 部署运维系列 · 第二批（DM21–DM35，9/29，未发布）

### DM21. ⚪ GPU 租用 vs 购买：算一笔账

GPU 的租买经济账：**租**（RunPod/AutoDL 约 $0.2-0.5/小时，4090 级别）适合实验期（每次几小时）——**买**（4090 约 $1,600）适合日均使用 >4 小时（6 个月回本）。

临界点：**日均使用 >4 小时 → 买；<4 小时 → 租。**

*核查：⚠️ 价格随行情浮动，发布前核对。*

### DM22. ⚪ 多模型部署的资源分配

一台 48G 服务器跑多个模型（7B + 3B + embedding）的资源分配：**7B 量化 6G + 3B 量化 3G + embedding 1G + 推理余量 10G = 20G**——剩余 28G 留给并发缓冲。

多模型共存的调度：**按请求类型路由**（简单→3B、复杂→7B、检索→embedding）。

*核查：✅*

### DM23. ⚪ 服务的日志聚合：ELK 的轻量替代

小团队的日志聚合不需要 ELK 全家桶（太重）：**结构化 JSON 日志 → 写文件 → grep 分析**——简单够用。

日志的内容：时间戳、用户 ID（脱敏）、输入输出摘要、耗时、token 数、错误码。

**日志的用途：排障 + 审计 + 成本分析 + bad case 发现**——四合一。

*核查：✅*

### DM24. ⚪ 提示词版本管理工具：从文本到平台

提示词版本管理的工具升级路径：**文本文件**（起步）→ **Google Sheet**（团队协作）→ **专业平台**（PromptLayer/Langfuse——评测+版本+监控一体）。

升级的触发：**当你在找"上周那个效果最好的提示词"花了超过 5 分钟**——该升级了。

*核查：✅*

### DM25. ⚪ 模型热更新：不重启服务换模型

模型热更新的实现：**模型文件外置**（不在 Docker 镜像里）、**热加载接口**（通知服务重新加载模型）、**灰度切换**（10% 流量用新模型）。

热更新的价值：**新模型上线不需要用户重新连接**——切换时间从分钟到秒。

*核查：✅*

### DM26. ⚪ A/B 测试的流量分配

A/B 测试的流量分配策略：**固定比例**（5% 新版 / 95% 旧版——最简单）、**按用户分组**（同一用户始终同一版本——体验一致）、**按时间切换**（上午 A 下午 B——适合对比明显的场景）。

流量分配的实现：**一致性 hash**（同一用户始终路由到同一版本）——不是随机（随机会导致同一用户体验不一致）。

*核查：✅*

### DM27. ⚪ 用户的 API 密钥管理

用户的 API 密钥管理的安全四原则：**加密存储**（AES-256，密钥分开管理）、**最小暴露**（日志和错误信息里永远不出现完整 key）、**定期轮换**（90 天一轮）、**权限分离**（每个 key 只能访问该用户的数据）。

密钥泄露的代价：**用户数据泄露 + 你的服务被滥用产生天价账单。**

*核查：✅*

### DM28. ⚪ 负载均衡：多实例的流量分配

多个 GPU 实例的负载均衡策略：**轮询**（平均分配——最简单）、**最少连接**（给最空闲的实例——适合长任务）、**加权**（按 GPU 性能分配——不同型号混部时用）。

健康检查：**每个实例定期 ping**（不健康的实例自动摘除，流量转到健康实例）。

*核查：✅*

### DM29. ⚪ 数据库备份策略：3-2-1 原则

数据备份的 3-2-1 原则：**3 份拷贝、2 种介质、1 份异地**。

AI 服务的备份数据：用户数据（必须）、微调 adapter（必须——训练了三天不能丢）、提示词版本（必须）、日志（可选）。

备份的测试：**定期做恢复演练**——备份了你恢复不了 = 没备份。

*核查：✅*

### DM30. ⚪ 服务健康检查：两个端点

服务健康检查的两个端点：**/health**（轻量——"服务活着吗"，不做任何计算）和 **/ready**（重量——"模型加载好了吗、依赖通了"，做一次实际推理测试）。

健康检查的频率：**每 30 秒一次**（负载均衡器用）——不健康的实例自动摘除流量。

*核查：✅*

### DM31. ⚪ CDN 与静态资源：前端的加速

LLM 应用的前端部署（如果有的话）：**静态资源（JS/CSS/图片）走 CDN**（全球加速）、**API 走自建**（模型推理不能走 CDN）。

前端的 AI 相关优化：**流式 UI**（SSE 接收 token 逐个渲染）、**乐观 UI**（先显示"正在生成"再填充内容）、**错误重试**（网络闪断时自动重试）。

*核查：✅*

### DM32. ⚪ WebSocket 长连接：流式输出的底层

流式输出的底层是 **SSE（Server-Sent Events）**或 **WebSocket**：

**SSE**：单向（服务→客户端），简单，适合"AI 生成→用户看"的单向流。
**WebSocket**：双向（客户端也能发），适合"对话式"实时交互。

选型：**简单流式用 SSE，实时双向对话用 WebSocket。**

*核查：✅*

### DM33. ⚪ Docker 镜像优化：从 5GB 到 500MB

AI 服务 Docker 镜像的优化：**多阶段构建**（构建阶段用大镜像，运行阶段用小镜像）、**层缓存**（不改依赖就不重装）、**.dockerignore**（排除模型权重/缓存文件）。

**镜像从 5GB 优化到 500MB** = 部署时间从 10 分钟到 1 分钟。

*核查：✅*

### DM34. ⚪ 监控的告警规则设计

告警规则的设计（不多不少刚刚好）：**错误率 >5%**（持续 5 分钟）→ 紧急告警、**P95 延迟 >10s**（持续 10 分钟）→ 警告、**token 成本日增 >50%** → 通知、**GPU 显存 >90%** → 警告。

告警的原则：**每条告警都要有对应的处理动作**——没有处理动作的告警，删掉。

*核查：✅*

### DM35. ⚪ 安全渗透测试：上线前的最后一关

AI 服务的渗透测试清单：**注入测试**（提示词注入/SQL 注入）、**越权测试**（用户 A 能否访问用户 B 的数据）、**拒绝服务**（大输入/高频请求能否打挂）、**密钥泄露**（日志/错误信息里有没有暴露密钥）、**内容安全**（能不能诱导生成有害内容）。

渗透测试的频率：**每次重大更新前跑一遍**。

*核查：✅*

# 部署运维系列 · 第三批（DM51–DM65，10/1，未发布）

### DM51. ⚪ 监控的 AI 化：用 AI 管 AI

用 AI 管理 AI 服务的监控：**异常检测**（AI 自动识别异常模式——比规则引擎更灵活）、**根因分析**（AI 分析日志找出问题根源）、**预测性告警**（AI 预测"即将出问题"而不是"已经出问题"）。

AI 监控的价值：**从"被动响应"到"主动预防"**——在问题影响用户之前解决它。

*核查：✅*

### DM52. ⚪ 日志分析的 AI 化

AI 分析日志的价值：**从百万行日志中找出异常模式**——人工搜索是大海捞针，AI 分析是鱼 finder。

分析的方法：**模式识别**（正常日志 vs 异常日志的模式差异）、**关联分析**（多个"看起来正常"的事件组合可能是攻击）、**趋势分析**（性能下降的趋势提前预警）。

*核查：✅*

### DM53. ⚪ 告警的智能化

告警的智能化：**减少告警疲劳**——太多告警 = 忽略所有告警。

AI 优化的告警：**自动聚合**（相关告警合并成一条）、**自动分级**（AI 判断严重程度）、**自动降噪**（AI 识别重复告警并抑制）、**自动路由**（AI 判断该通知谁）。

*核查：✅*

### DM54. ⚪ 容量预测：AI 预测资源需求

AI 预测资源需求：**基于历史趋势预测未来的 GPU/存储/带宽需求**——

预测的价值：**提前采购**（GPU 到货要 4-8 周）、**提前优化**（预测到瓶颈就提前调优）、**提前降本**（预测到低峰期就释放资源）。

*核查：✅*

### DM55. ⚪ 成本的自动优化

成本的自动优化：**AI 自动选择最优配置**——

自动选择：**哪个模型**（按任务复杂度路由）、**哪个时间**（按电价峰谷调度）、**哪个区域**（按延迟和成本路由）、**哪个方案**（缓存命中就走缓存）。

*核查：✅*

### DM56. ⚪ 安全扫描的自动化

安全扫描的自动化流水线：**依赖扫描**（已知漏洞的依赖库）、**代码扫描**（安全编码规范）、**注入测试**（提示词注入/SQL 注入）、**配置扫描**（不安全的配置项）、**权限审计**（权限过宽的检查）。

*核查：✅*

### DM57. ⚪ 合规检查的自动化

## FAQ 与实战篇（DM81–105，10/1）

### DM81. ⚪ 第一台服务器怎么选：冷启动部署决策

新项目第一台服务器，按三个问题选：

一、**流量可预期吗**？demo/内测阶段，$5-10 的轻量 VPS 足够——别为想象中的流量付费；

二、**有 GPU 需求吗**？要跑本地模型就从租用 GPU 开始（按小时计费），绝对别上来就包月；

三、**你熟悉什么**？选你熟的云，省下的踩坑时间比差价值钱。

冷启动的最大陷阱是"一步到位"思维——架构师式地规划"百万用户架构"，结果项目死在了上线前。**先跑起来，让真实流量教育你**。

### DM82. ⚪ 一步到位的 CI/CD：GitHub Actions 最小配置

小项目的 CI/CD 不需要 Jenkins 那套，GitHub Actions 三步最小配置：

第一步，push 触发：跑 lint + 单测（10 分钟内必须完成，否则没人等它）；

第二步，测试过了自动构建镜像并推送；

第三步，手动确认后部署到服务器（早期保留手动这步，相当于免费的灰度）。

两个纪律：主分支保护打开（禁止直接 push）、部署脚本进仓库（别在你的笔记本上）。

这套配置的成本是一小时搭建，收益是之后每次上线的十分钟和零遗漏。

### DM83. ⚪ 环境三分法：开发/预发/生产的最低要求

"我本地是好的"——这句话的解药是环境分离。小团队的最低要求：

**开发环境**：本地跑，随便折腾，用测试凭证；

**预发环境**：和生产同配置（同版本数据库/同参数），用脱敏数据，上线前最后一关；

**生产环境**：只允许通过 CI 部署，人工不直接改（改了就叫"漂移"，迟早爆雷）。

预算紧张的省法：预发和生产共享架构但降配（生产 4C8G，预发 1C2G）——**配置可以缩，结构不能省**，否则预发失去意义。

### DM84. ⚪ Secrets 管理：.env 文件之外的世界

密钥管理的进化路线，按团队规模走：

个人项目：.env 文件 + **确保 .gitignore 生效**（每年仍有无数密钥泄漏在公开仓库里）；

小团队：环境变量注入到部署系统（CI 的 secrets 功能），密钥不再出现在任何文件里；

再进一步：密钥管理服务（Vault 类）+ 自动轮换。

一条铁律不分规模：**密钥泄漏的第一反应是撤销重发，不是删除仓库**——git 历史里它永远都在。

### DM85. ⚪ 域名与 HTTPS：证书自动续期配置

证书过期是最低级的线上事故——而它完全可以自动化消失。

Let's Encrypt + 自动续期（certbot 的定时任务或云负载均衡的托管证书）配好之后，你唯一要做的是**监控续期是否真的在跑**：加一条"证书剩余天数 < 14 天就告警"的监控。

为什么还要监控：续期任务可能因为 DNS 变更、端口封锁而静默失败——自动化系统也需要被监督。

一次性 30 分钟的配置，消灭一类凌晨事故，这是运维里回报率最高的动作之一。

### DM86. ⚪ 数据库迁移：改 schema 不停机的路数

改表结构的正确姿势（小项目也适用）：

**扩展-迁移-收缩**三步法：第一步，加新列/新表（旧代码完全不受影响）；第二步，双写过渡（新代码同时写新旧两处，回填历史数据）；第三步，切换读路径，观察一周后删除旧结构。

核心纪律：**每一步都可回滚，任何一步出错都不影响线上**。

反面教材是"直接 ALTER 大表"——锁表期间服务全挂，你们会一起上事故复盘会。

### DM87. ⚪ 静态站 vs 动态服务：部署位置的选择

新项目往哪放，先问一个问题：**有服务端逻辑吗**？

纯静态（落地页、文档、博客）：静态托管（Pages/Vercel 免费档），CDN 全球加速，零运维；

有 API 的轻应用：前端静态托管 + 后端轻量容器，分离部署；

重后端（模型服务、数据管道）：传统容器/云主机。

常见的反模式：把纯静态页面也架在一台 VPS 上 nginx 伺候——多了运维对象，少了全球加速。**能静态的都静态，动态的才上服务器**。

### DM88. ⚪ Serverless 的边界：什么时候不适合函数计算

函数计算（Serverless）省钱省心，但有三个不适合的信号：

一、**长任务**——函数有执行时长上限，跑 20 分钟的数据处理别塞进函数；

二、**稳定高流量**——函数按调用计费，流量恒定时比常驻容器贵 2-5 倍（它的甜点是"波动流量"）；

三、**GPU 需求**——模型推理的冷启动+租卡模式还早，老实用容器。

它的甜点场景：webhook 处理、定时任务、突发性的轻逻辑。**用对场景是神器，用错场景是账单刺客**。

### DM89. ⚪ 容器日志清理：磁盘不被日志吃掉

跑了几个月的服务器磁盘悄悄满了，八成是日志。三个防线：

一、**容器日志轮转**——Docker 默认不限制日志大小（json-file 驱动会无限写），启动时配 max-size=10m, max-file=3；

二、**应用日志分级**——INFO 以上才落盘，DEBUG 只在排障时临时开；

三、**磁盘监控**——使用率 80% 告警，别等 100% 时连登录都卡。

急救口诀（磁盘已满时）：`docker system prune` 清镜像缓存 → 大日志文件 truncate → 找根因。

### DM90. ⚪ Nginx 反代 AI 服务：超时与缓冲的两个坑

用 nginx 反代 AI 接口，两个必踩的坑提前说：

一、**超时**——LLM 生成动辄几十秒，nginx 默认 60 秒断连：`proxy_read_timeout 300s` 按最慢接口调；

二、**缓冲**——默认开缓冲会攒齐再发，流式输出变成"卡住然后一次性蹦出来"：`proxy_buffering off` 恢复流式体感。

第三个小坑是请求体大小：上传文件的接口记得调 `client_max_body_size`。

这三行配置能消灭"AI 服务部署后体验奇怪"的 80% 工单。

### DM91. ⚪ 定时任务的管理：cron 的现代替代

服务器上的 cron 三个经典问题：挂了没人知道、日志找不到、依赖的服务没起来它照跑。

现代替代方案按复杂度选：单机小任务——cron + **失败通知**（每条任务尾部挂告警脚本）；跨服务任务——工作流引擎（n8n / Temporal 类），带重试、可视化、执行历史；云上——托管定时任务（EventBridge 类），免维护。

无论哪种，一条纪律：**每个定时任务必须有"最近一次运行状态"可见**——不可观测的定时任务是定时炸弹，字面意思。

### DM92. ⚪ 服务依赖地图：你的服务挂着谁的

画一张你自己服务的依赖地图，通常会有惊喜（惊吓）：

显式依赖：数据库、模型 API、对象存储；

隐式依赖：DNS 服务商、证书签发、CDN、支付回调、第三方登录、邮件服务。

把隐式的全部显式化，然后给每个依赖标两列：**挂了会怎样**（全挂/降级/无感）、**多久能恢复**（自动/手动/听天由命）。

这张表的价值：故障时你按图索骥而不是抓瞎，架构演进时你看得见哪个依赖成了单点。一小时画图，值回票价。

### DM93. ⚪ 降级开关：峰值时刻的功能开关

提前在代码里埋好"降级开关"，出事时的一键保命：

典型开关：**关闭非核心功能**（推荐、统计、动画——用户感知低、资源消耗高）、**静态兜底**（AI 生成接口挂了返回缓存结果）、**排队机制**（超出容量进入等待而非报错）。

实现要点：开关状态放配置中心或 Redis，**不随代码发版**——发版是分钟级，救火是秒级。

测试开关的唯一方式：定期真的扳一次。从没被扳过的开关，出事那天大概率是坏的。

### DM94. ⚪ 长任务的后台化：任务队列入门

HTTP 请求里跑 30 秒以上的任务，迟早出三连：网关超时、用户重复提交、服务被拖死。解法是任务队列：

三件套：**任务入队**（HTTP 接口收到请求，校验后塞进队列，立刻返回任务 ID）、**worker 消费**（后台进程按能力取任务执行）、**状态查询**（前端轮询或 WebSocket 拿进度）。

轻量选型：个人项目用 Redis + 简单队列库足够；重需求（优先级、定时、重试策略）再上 Celery/BullMQ 类。

核心思想：**请求要快，任务要慢**——快慢分离是服务稳定的分水岭。

### DM95. ⚪ 优雅停机：滚动更新不丢请求

部署新版本的那几秒里丢请求？缺的是优雅停机：

三个环节：**停止接新**（先从负载均衡摘除，不再有新流量进来）、**跑完在手**（给进行中的请求 15-30 秒宽限期处理完）、**清理资源**（关数据库连接、刷缓冲区，然后退出）。

容器化的实现：处理 SIGTERM 信号 + 配置 terminationGracePeriod。

验证方法：压测时滚动更新，看错误数——**零错误**才算优雅。这个配置每次上线都在保护你，只是你从没发现它工作过。

### DM96. ⚪ 内存泄漏排查：从 OOM 到定位

服务跑几天就 OOM 重启，排查路径四步：

一、**确认泄漏形态**——看内存曲线：锯齿状回落（正常 GC）还是阶梯状只涨不跌（泄漏）；

二、**锁定进程**——容器里区分"应用泄漏"还是"缓存无上限"；

三、**抓堆快照**——泄漏进程的 heap dump 前后对比，找增长最快的对象类型；

四、**对号入座**——高频泄漏惯犯：无界缓存（字典只写不清）、连接未关闭、监听器反复注册、大对象进了全局。

临时缓解用"定时重启"（低峰期），但那是止痛药——根因定位前别停查。

### DM97. ⚪ CPU 100% 的排查路径

CPU 打满时的按序排查，别上来就重启：

一、**定位线程**——top -H 看哪个线程烧的（Java/Python 各有对应工具映射到代码行）；

二、**判断类型**——死循环（单个线程 100% 且持续）还是负载过量（多线程均匀高）；

三、**死循环**——抓栈直接看卡在哪一行，通常是新上线的循环条件 bug；

四、**负载过量**——看请求量是否异常（被打、被爬、活动流量），要么扩容要么限流，代码没病。

重启是最后的手段，因为它会**销毁现场**——下一次抓贼就没有证据了。

### DM98. ⚪ 磁盘满的三分钟急救

磁盘 100% 的三分钟急救流程（先恢复，后追凶）：

第一分钟：`df -h` 确认哪个分区满 → `du -sh /*` 逐层下钻找大目录；

第二分钟：安全的删除目标——旧日志（truncate 而非 rm 正在写的文件）、Docker 悬空镜像（prune）、临时文件；

第三分钟：确认服务恢复 + **立刻加磁盘告警**（80% 触发）。

追凶放到恢复之后：日志疯长、备份堆积、数据库 WAL 暴涨，各有各的根治法——但先让服务喘气。

### DM99. ⚪ DNS 问题的排查常识

"服务好好的，部分用户访问不了"——先查 DNS 再查服务。常识四条：

一、**DNS 有缓存**——你改了记录，全球生效要等 TTL（默认可能几小时），"改了怎么还没好"多数是这个；

二、**分域定位**——`dig`/`nslookup` 对比：权威 DNS 对 vs 本地解析错 = 缓存问题；都对但连不上 = 不是 DNS 的锅；

三、**TTL 的事前设计**——计划中的迁移提前 24 小时把 TTL 调短到 300 秒；

四、**解析正常但 IP 错了**——检查是不是有两个 A 记录/CNAME 冲突，老记录没删。

### DM100. ⚪ 证书过期事故：一次凌晨告警的教训

讲个真实教训（自己踩的）：凌晨两点证书过期，网站全挂，而续期脚本"明明配置了"。

事故链：续期任务依赖的 DNS 验证方式变更 → 任务静默失败三个月 → 没有任何监控盯着"证书剩余天数" → 用户先于我发现。

修复三件套：续期自动化（本来就有）、**剩余天数监控（当时没有，补上）**、续期后自动验证（curl 检查新证书生效）。

教训一句话：**自动化的最后一公里是"确认自动化在跑"**——所有静默失败的定时任务都是未来的凌晨事故。

### DM101. ⚪ 单点风险清单：一人运维的依赖盘点

一人运维的项目，把"你"也算进单点风险。完整盘点：

技术单点：一台服务器、一个数据库、一个模型供应商（都是已知单点，至少要有备份和替代路径）；

**人的单点**：密码只在你脑子里？部署只会在你笔记本上跑？凌晨出事只有你知道架构？

最低配置的三件解药：密码进管理器、部署脚本进仓库 + 一页"新人接手指南"、一个能联系上的 backup 人（朋友/社区/外包）。

一人公司可以一人干活，但**不能一人失联**——这句话写给三年前没做任何准备的自己。

### DM102. ⚪ 运维交接文档：三页纸的最低要求

运维知识最低限度要写下来三页，别管文采：

第一页，**地图**：有哪些服务、跑在哪、域名指向谁、数据库有几个——一张架构图加一个清单；

第二页，**钥匙**：什么账号在哪管理（指向密码管理器，不写密码本身）、怎么 SSH、怎么进数据库；

### DM103. ⚪ 从单机到多机的触发条件

"要不要拆成多台服务器"——别按玄学决策，按信号：

该拆的信号：**单点故障影响业务收入**（一台挂全站死，且死了真亏钱）、单机资源持续 70%+（扩容无门）、不同服务的资源特性互相干扰（数据库和任务脚本抢内存）；

不该拆的信号：流量稳定、单机还有余量、"感觉多机更专业"（这是最贵的感觉）。

过渡的正确第一步不是拆成两台，而是**把单机上的服务容器化**——先分离逻辑，再分离物理。顺序反了的人，都在多机上跑着单机版的混乱。

### DM104. ⚪ 云成本月审：一小时省 30% 的流程

每月第一个周五，一小时的云成本月审（实测平均能省 20-30%）：

第一查，**僵尸资源**——没流量却活着的实例、没绑负载的弹性 IP、创建后忘记的测试数据库（云厂商不会提醒你）；

第二查，**超配资源**——CPU 常年 5% 的实例降配、用不满的存储包换小档；

第三查，**计费异常**——本月比上月涨的部分，逐项找到原因（流量突增要查是不是被爬/被打）；

第四查，**预留券**——长期稳定负载换包年/预留实例，通常省 30-60%。

审计的副产品：你对成本结构的理解，比 90% 的同行清楚。

### DM107. ⚪ 液冷运维：漏液是新的故障

### DM110. ⚪ 观测数据的采样策略

观测数据的采样策略（可观测性的成本与覆盖权衡）：

全量观测的成本现实：**trace 全量的存储成本 = 业务成本的 10-20%**（AG 系列日志的代价）——**采样是必修课**；

**采样的四种策略**：**头部采样**（固定比例——简单但可能漏掉罕见错误）、**尾部采样**（**先看全量，保留错误的+抽样的正常的**——**错误永不丢失**——**生产推荐**）、**基于规则的采样**（慢调用/错误调用 100% 保留——**有价值的多留**）、**自适应采样**（**异常时段自动提高采样率**——**出事时看得最清**）；

**采样的对偶原则：故障排查需要的 trace，永远不在你采样的样本里**——**对策：尾部采样+错误全保留+**"出事时动态提采样率"**——**采样的目标不是"省"，是"出事时一定有证据"。**
