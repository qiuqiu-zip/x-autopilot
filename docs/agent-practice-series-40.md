# Agent 实战系列 · 草稿（AG1–AG30，9/28，未发布）

> 板块二首批。定位：从概念到实战的 Agent 工程系列。
> 核查标记：✅ 共识/已验证 ｜ ⚠️ 需自测或时效内容

### AG1. ⚪ Agent 的解剖：模型 + 工具 + 循环

剥掉所有框架包装，Agent 就是三件套：

**模型**（大脑，负责决策）+ **工具**（手脚，负责执行）+ **循环**（心跳，负责持续工作）。

模型收到任务 → 决定调用哪个工具 → 拿到结果 → 决定下一步 → 循环，直到任务完成。

所有框架（LangGraph/CrewAI/自研）都是这三件套的不同封装。理解了骨架，框架只是方言。

*核查：✅*

### AG2. ⚪ 工具设计第一原则：让 Agent 容易做对

给 Agent 设计工具，第一原则不是功能强大，是**容易用对**：

工具名自解释（search_orders 好过 so2）、参数少而明确（必填参数 ≤3 个）、返回值结构化（JSON + 明确的成功/失败标记）、报错信息可读（Agent 要根据报错自我修正）。

一个反例：把 10 个功能塞进一个工具、参数是个嵌套 JSON——Agent 的调用错误率会翻几倍。

*核查：✅*

### AG3. ⚪ 工具描述 = Agent 的说明书

Agent 选择工具的依据，完全来自你在工具描述里写的话。

差的描述："搜索工具"——Agent 不知道什么时候该用它。
好的描述："搜索历史订单。输入：6 位数字订单号。返回：订单状态和物流信息。当用户询问已购商品的配送或状态时使用；新订单查询不适用。"

**使用场景 + 输入格式 + 返回内容 + 不适用的边界**——四件套写全，Agent 的工具选择准确率直接上一个档。

*核查：✅*

### AG4. ⚪ 函数调用实战：从提示词到结构化输出

Agent 的"调工具"底层是函数调用（Function Calling）：模型输出结构化的 JSON（工具名 + 参数），你的代码执行它，把结果喂回去。

实战细节：用各家原生的 function calling 接口（比自己写提示词解析稳）；参数 schema 定义得越严格（枚举、格式约束），错误率越低；**永远校验模型给的参数再执行**——它偶尔会幻觉出不存在的参数值。

*核查：✅*

### AG5. ⚪ ReAct：思考-行动-观察的循环

最经典的 Agent 模式叫 ReAct，每轮三步：

**思考**（我该干什么）→ **行动**（调用工具）→ **观察**（结果是什么）→ 循环。

它的价值不是流程本身，是**思考过程可见**——你能看到 Agent 为什么这么决策，错了知道错在哪一步。

自己写 Agent，从 ReAct 循环开始就够了，先别碰花哨架构。

*核查：✅*

### AG6. ⚪ 任务拆解：Agent 的规划从哪来

复杂任务（"分析这个季度的销售数据并写报告"）需要 Agent 自己拆步骤。三种来源：

**让它自己拆**（简单任务够用）、**你预拆好步骤**（稳定但僵硬）、**混合**（你给大纲，它填细节）。

实测建议：生产环境用混合模式——**大纲你定，路径它选**。完全放权的 Agent，一半概率跑偏。

*核查：✅*

### AG7. ⚪ 记忆三层：短期、工作、长期

Agent 的记忆分三层，别混：

**短期**：当前对话的上下文（自动有，关了就没）
**工作记忆**：任务执行中的中间状态（变量、文件、TODO 列表——需要你设计）
**长期**：跨会话的记忆（向量库/数据库——需要你建）

最常见的错误：把所有记忆都塞进上下文窗口。窗口是工作台不是仓库——三层各司其职。

*核查：✅*

### AG8. ⚪ 上下文管理：修剪的艺术

Agent 跑久了，上下文被工具结果塞爆。修剪的艺术：

**工具结果摘要化**（1000 字的搜索结果压缩成 100 字要点再进上下文）、**旧轮次归档**（把早期对话移到外部存储，需要时检索）、**关键信息锚定**（任务目标和重要约束每隔几轮重申一次，防"漂移"）。

上下文管理做得好，长任务的稳定性提升一个量级。

*核查：✅*

### AG9. ⚪ 错误处理：重试、降级、兜底

Agent 的错误处理三层：

**重试**（网络抖动类错误，指数退避重试 2-3 次）、**降级**（主工具挂了换备用工具：搜索 API 挂了换另一个搜索引擎）、**兜底**（都不行就如实报告，别硬编结果）。

铁律：**Agent 失败时要说"我失败了，原因是 X"**——编造一个看起来成功的假结果，是 Agent 最危险的失败模式。

*核查：✅*

### AG10. ⚪ 沙箱：Agent 的安全区

Agent 执行代码、操作文件、访问网络——每个能力都是风险面。沙箱原则：

**代码执行**放隔离环境（容器/沙箱，别在主机裸跑）、**文件操作**限定目录（Agent 只能碰指定文件夹）、**网络访问**白名单制、**危险动作**（删除、支付、外发）必须人工确认。

沙箱不是限制 Agent 的能力，是让你敢给它能力。

*核查：✅*

### AG11. ⚪ 成本控制：token 预算制

Agent 跑飞了的另一个代价：token 烧钱。预算制三招：

**任务级预算**（单任务设 token 上限，超了就收束输出）、**工具选择分级**（简单查询用便宜模型，复杂决策用贵的）、**结果缓存**（重复查询走缓存，不重新推理）。

账单翻倍的 Agent，通常不是任务变难了，是循环失控了（见 AG25）。

*核查：✅*

### AG12. ⚪ Human-in-the-loop：审批节点的设计

高风险动作（发帖、付款、删数据）前插入人工审批——设计要点：

**审批点前置声明**（Agent 的计划里写明哪些步骤会请求审批）、**审批内容要完整**（给人类看的是"将要执行什么"，不是"我想执行什么"）、**批量审批的粒度**（同类操作可批量，危险操作逐条）。

我们运营 X 账号的实践：密码和验证码永远人工，发帖内容可批量预审——这就是审批节点的实例。

*核查：✅*

### AG13. ⚪ Agent 评测：任务成功率是唯一硬指标

Agent 的评测比聊天模型更实在：**任务成功率**（给 50 个真实任务，看完成多少）、**平均成本**（每任务 token 消耗）、**平均时长**、**失败模式分类**。

聊天模型可以凭感觉，Agent 必须跑任务清单——因为 Agent 的产出是行动，行动的对错是客观的。

每次改提示词或换模型，重跑任务清单。没有任务清单的 Agent 开发是玄学。

*核查：✅*

### AG14. ⚪ 单 Agent vs 多 Agent：先单后多

"要不要上多 Agent 架构？"——先问三个问题：

任务能拆成**真正独立**的子任务吗？子任务需要**不同工具集**吗？单 Agent 的上下文**装不下**所有工具吗？

三个都是"是"，才考虑多 Agent。否则单 Agent + 好工具 + 好循环，更快、更便宜、更好调试。

*核查：✅*

### AG15. ⚪ 多 Agent 模式一：主管-工人

最常用的多 Agent 模式：一个**主管 Agent** 接任务、拆解、分发；多个**工人 Agent** 各有专长（搜索员、写手、审查员）执行。

设计要点：工人只对自己的子任务负责（上下文干净）、主管做汇总和质量把关、工人之间的通信通过主管中转（别让他们私聊，会失控）。

*核查：✅*

### AG16. ⚪ 多 Agent 模式二：流水线

内容生产类任务适合流水线：**调研 Agent → 写作 Agent → 审核 Agent → 发布 Agent**，每个环节的输出是下一个环节的输入。

设计要点：每个环节定义清晰的输入输出格式（像接口一样）、环节间加质检（不合格打回上游）、流水线的瓶颈环节可以并行多个实例。

我们的账号内容供给，本质就是这条流水线。

*核查：✅*

### AG17. ⚪ 多 Agent 模式三：辩论与评审

高质量决策场景用辩论模式：**多个 Agent 独立作答 → 互相评审对方的方案 → 仲裁者（人或强模型）定稿**。

价值：独立视角能暴露单一 Agent 的盲区。成本：token 消耗是单 Agent 的 3-5 倍。

适用判断：错误代价高的决策（合同、医疗、发布内容）值得辩论；日常任务别浪费。

*核查：✅*

### AG18. ⚪ 框架选择：LangGraph / CrewAI / 自研循环

框架选择的诚实建议：

**自研循环**（AG5 的 ReAct，100 行代码）：学习期和简单任务——没有黑盒，完全可控。
**LangGraph**：复杂状态机和流程控制需求。
**CrewAI**：快速搭多角色协作原型。

反直觉建议：**从自研循环开始**。理解了裸循环，框架才是助力；直接上框架，出了问题你连错在哪一层都找不到。

*核查：✅*

### AG19. ⚪ MCP：Agent 的 USB 接口

MCP（Model Context Protocol）统一了 Agent 连接工具的方式：以前每接一个工具要写一套胶水代码，现在都是标准插座。

对 Agent 工程的意义：工具生态爆发——别人写好的 MCP 服务（搜索、数据库、浏览器），你的 Agent 直接接。

呼应大模型系列 M13 的类比：MCP 统一插头，Marketplace 统一货架。

*核查：✅*

### AG20. ⚪ 案例一：内容运营 Agent（活体案例）

本号的运营就是一个活的 Agent 案例：**扫描目标帖 → 按定位生成回复 → 人工或自动发布 → 记录互动数据 → 反馈优化**。

架构：自研 ReAct 循环 + 真实 UI 通道（绕风控）+ 人工审批节点（内容发布前）。

这就是"Agent 工程"不需要大厂资源的证明：一个循环、几个脚本、一套规则，跑通了完整闭环。

*核查：✅ 本号即案例。*

### AG21. ⚪ 案例二：代码 Agent 的工具集

代码 Agent（如 Claude Code 类）的工具集值得拆解学习：读文件、写文件、执行命令、搜索代码库——**每个工具都对应程序员真实工作的一步**。

可借鉴的设计：工具少而精（6-8 个核心工具覆盖 90% 场景）、执行类工具必须跑在沙箱、给 Agent 看到运行结果的能力（输出回填）。

*核查：✅*

### AG22. ⚪ 案例三：研究 Agent（Deep Research 类）

Deep Research 类 Agent 的流程拆解：**任务理解 → 拆解研究问题 → 多源搜索（迭代）→ 交叉验证 → 结构化报告**。

关键技术：搜索结果的**去重与可信度评分**、研究中途的**子问题修正**（发现新线索时调整方向）、最终报告的**来源标注**。

它的产出之所以可信，是因为每一步都有来源——单靠模型编不出可信的研究。

*核查：✅*

### AG23. ⚪ 案例四：客服 Agent 的边界设计

客服 Agent 的设计重点不是能力，是**边界**：能答什么（产品/流程/状态）、必须转人工什么（投诉/退款纠纷/情绪激动）、绝不做什么（承诺赔偿、透露内部信息）。

边界清单写进系统提示词 + 转人工机制做成工具（Agent 主动调用"转人工"）。

客服 Agent 的事故，90% 是边界设计缺失，不是模型不够聪明。

*核查：✅*

### AG24. ⚪ 案例五：数据分析 Agent 的工具链

数据分析 Agent 的标准工具链：**执行 SQL 的工具 + 读取图表的工具 + 计算工具**。

设计要点：给 Agent 看**表结构文档**（schema 是它的领域知识）、SQL 执行结果回填让它能迭代修正、生成图表作为交付物。

它不会取代数据分析师——它取代的是分析师写 SQL 的时间，分析师的时间转向"问对问题"。

*核查：✅*

### AG25. ⚪ 失败模式一：无限循环

Agent 最经典的翻车：在两个动作之间死循环（搜索→没找到→换个词再搜→还没找到→再搜……）。

防线：**循环次数上限**（硬编码，比如 15 轮必须收束）、**重复检测**（连续两次动作相同就强制换策略）、**预算熔断**（token 超限强制终止并报告）。

三道防线都是几行代码，但没有它们，一次跑飞就是一晚上电费。

*核查：✅*

### AG26. ⚪ 失败模式二：工具滥用

Agent 拿到 10 个工具，会用 2 个解决所有问题——因为那 2 个的描述写得最好。

解法不是删工具，是**描述里写清分工边界**（"X 用于实时数据，Y 用于历史数据"）、**移除任务用不到的工具**（工具越少，选择越准）、**观察调用分布**（某工具从未被调用，要么删掉要么改描述）。

工具集是 Agent 的能力边界，也是它的偏见来源。

*核查：✅*

### AG27. ⚪ 失败模式三：上下文膨胀

长任务跑到一半，Agent 开始"失忆"、重复劳动、答非所问——查上下文，早就被工具结果塞爆了。

防线：AG8 的修剪策略 + **工具结果不入上下文**（大结果写文件，上下文里只留摘要+文件路径）+ **阶段性总结**（每完成一个子任务，生成 3 句话总结替换原始过程）。

上下文是 Agent 的工作台——工作台乱了，什么活都干不好。

*核查：✅*

### AG28. ⚪ Agent 的经济学：成本收益的临界点

Agent 替代人工的经济学账：**单任务成本（token+时长）vs 人工成本 × 频次**。

现状参考：简单研究/整理任务，Agent 成本 $0.1-1，人工 30-60 分钟——划算。复杂创造性任务，Agent 产出需要大量人工修正——不划算。

策略：**从"人工做的最烦的那件事"开始自动化**，那里 ROI 最高。

*核查：✅*

### AG29. ⚪ Agent 的安全边界：攻防已经在发生

Agent 能操作电脑，恶意 Agent 也能——安全议题已经实战化：**提示词注入**（网页里藏指令劫持 Agent）、**数据外泄**（Agent 被诱导发送敏感信息）、**权限滥用**。

防御（呼应 FT214/AG10）：沙箱隔离、权限最小化、关键动作人工确认、来源可信度评估。

你的 Agent 连着你的账号、你的数据、你的钱包——安全设计不是可选项。

*核查：✅*

### AG30. ⚪ 收束：Agent 工程的终极问题是信任

30 篇写完，Agent 工程的核心问题浮出水面：**你愿意把多大的决策权交给它？**

完全信任 = 效率最高 + 风险最大。完全不信 = 安全 + 没用了。

好的 Agent 工程是这个滑块的艺术：**低风险动作全自动，中风险动作抽样审，高风险动作逐条审**——滑块的位置随信任积累动态调整。

我们账号的滑块位置：内容生成自动、发布前人工抽审、身份操作永远人工。这就是当前的最优解，也会随着信任数据的积累慢慢右移。

*核查：✅ 系列收束。*
# Agent 实战系列 · 第二批（AG31–AG40，9/28，未发布）

### AG31. ⚪ Agent 的编排层：从循环到状态机

复杂 Agent 的编排进化：**从 while 循环到状态机**。

状态机把任务定义成明确的状态（理解→检索→起草→自查→完成）+ 状态间的转移条件——每个状态的提示词独立调优，转移条件显式可见。

好处：调试时知道卡在哪个状态、每个状态可独立评测、失败可从任意状态恢复。LangGraph 就是这个思路的产品化。

*核查：✅*

### AG32. ⚪ Agent 的上下文预算表

给 Agent 做预算表（每次任务的上下文分配）：

系统提示词 10% + 任务描述 10% + 少量示例 10% + **工具结果预算 50%**（大头）+ 思考空间 20%。

超预算的处置优先级：压缩旧工具结果 > 砍掉非关键检索 > 升级模型窗口。**预算表让"上下文膨胀"从玄学变成会计。**

*核查：✅*

### AG33. ⚪ Agent 间的交接协议（Handoff）

多 Agent 协作的交接（handoff）协议四要素：**任务摘要**（上游干了什么）、**中间产物**（文件/数据的位置）、**已知问题**（上游发现的坑）、**验收标准**（下游要做到什么程度算好）。

交接差的团队症状：下游 Agent 重复上游的工作、或在上游的坑上继续盖楼。

**交接协议 = Agent 团队的会议纪要。**

*核查：✅*

### AG34. ⚪ Agent 的自我批判（Self-Critique）循环

提升 Agent 质量的性价比之王：**生成后强制自我批判一轮**。

流程：生成答案 → 用批判提示词自查（"找错：事实、逻辑、格式、遗漏"）→ 修订 → 输出。

实测：一轮自我批判能修复 30-50% 的错误，成本只增加一次调用。**批判用同一个模型就有效**——它看自己的输出比看自己的推理更容易发现问题。

*核查：✅*

### AG35. ⚪ Agent 的记忆检索：什么时候翻档案

长期记忆（向量库）的检索时机设计：**不是每轮都检索**。

检索触发器设计：遇到专有名词/历史决策/用户偏好时检索，通用任务不检索。检索太频繁 = 上下文被旧记忆污染 + 成本翻倍。

记忆检索的正确心法：**像人类回忆一样——需要的时候才翻档案，且只翻相关的页。**

*核查：✅*

### AG36. ⚪ Agent 的观察窗口：结果要喂得多细

工具返回结果给 Agent 看，喂多细是个设计决策：

**全文喂**（上下文爆炸但信息全）、**摘要喂**（省上下文但可能丢关键细节）、**分层喂**（先摘要，Agent 要细节时再取全文）。

经验法则：**判断类结果喂全文**（Agent 要自己评估），**事实类结果喂摘要**（Agent 只需要结论）。

*核查：✅*

### AG37. ⚪ Agent 的行为一致性：同一任务跑一百次

Agent 的稳定性测试：**同一任务跑 100 次，统计成功率分布**。

单次成功不代表稳定——Agent 的输出是概率的。100 次跑出 85% 成功率的 Agent，意味着每 7 次任务失败 1 次——这个数据决定它能不能上生产。

**分布思维替代单次思维**，是 Agent 工程师的成熟标志。

*核查：✅*

### AG38. ⚪ Agent 的降级路径设计

每个 Agent 都要有降级路径（degradation path）：

**全功能模式** →（模型超时）→ **简化模式**（减少工具/缩短上下文）→ **兜底模式**（返回部分结果+明确说明未完成部分）。

用户对"部分完成+诚实说明"的容忍度，远高于"全量完成但等 5 分钟"或"直接报错"。

降级不是失败，是设计。

*核查：✅*

### AG39. ⚪ Agent 的可观测性：三根日志柱子

Agent 的可观测性三柱：

**决策日志**（每轮的思考与工具选择——为什么这么干）、**执行日志**（每次调用的输入输出与耗时——干了什么）、**成本日志**（每轮 token 消耗——花了多少）。

三柱合起来的能力：**回放任何一次任务执行的完整过程**——调试、审计、优化全靠它。

*核查：✅*
