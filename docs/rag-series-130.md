# RAG 全链路系列 · 草稿（RG1–RG20，9/28，未发布）

### RG1. ⚪ RAG 三步流程：检索、增强、生成

RAG（检索增强生成）三步：**你的问题 → 从知识库里找出最相关的几段资料 → 连同问题一起交给大模型回答。**

它解决两个致命问题：模型不知道你的私有数据、模型的知识有截止日期。

一句话记住：**RAG 是开卷考试——模型还是那个模型，但给它发了参考资料。**

*核查：✅*

### RG2. ⚪ 什么时候用 RAG：两个判断

两个判断，全中就用 RAG：**知识会变吗**（价格、政策、文档——会变的进知识库，别指望微调记住）、**知识是你的吗**（企业内部文档、个人笔记——模型天生不知道）。

都不中（纯创作、通用常识）→ 不需要 RAG，直接问。

*核查：✅*

### RG3. ⚪ RAG 效果差，七成问题在检索

RAG 效果差，多数人去改提示词——方向错了。

业界经验：**RAG 的失败七成在检索**（没找对资料），三成才在生成。找错了资料，模型拿着错误依据认真胡说。

所以调优顺序：先修检索（分块、embedding、rerank），再修生成（提示词）。本系列 20 篇的编排就按这个比例。

*核查：⚠️ 比例为经验归纳，非严格统计。常青。*

### RG4. ⚪ 文档分块：按语义切，不按字数切

知识库建的第一步是把文档切成小块。最大的坑：**按固定字数硬切**——把一段完整的话从中间腰斩。

正确姿势：**按语义切**（按段落/章节/主题边界）、块间保留 10-15% 重叠（防断章取义）、表格和代码块整块保留不切。

分块的质量决定检索的上限——切烂了的文档，后面神仙也检索不好。

*核查：✅*

### RG5. ⚪ 分块大小：没有标准答案，有测试方法

块多大合适？300 字、500 字还是 1000 字？**没有标准答案，只有测试方法**：

用你的真实问题集，测 3 种块大小（比如 256/512/1024），看检索命中率哪个高。

经验范围：问答场景 300-500 字、文档摘要场景 1000-2000 字。你的数据你说了算。

*核查：✅*

### RG6. ⚪ Embedding 模型选型：三个实测维度

选 embedding 模型（把文字变向量的模型）看三个实测：**中文效果**（用你的真实问题测命中率）、**速度**（百万级文档的入库时间）、**维度**（维度越高存储越贵）。

别只看 MTEB 榜单——**用你的数据实测**，结果经常和榜单不一致。开源的 BGE 系列是中文场景的常见起点。

*核查：✅*

### RG7. ⚪ 向量数据库选型：从简开始

向量数据库的选型焦虑可以治好：**数据量小于百万级，先用最简单的**。

入门：Chroma / FAISS（本地、免费、几行代码）
生产：Milvus / Qdrant / pgvector（Postgres 插件——已有 PG 的团队零成本新增）

先跑起来，数据量真上去了再换。**迁移的成本，低于一开始就上重装备的成本。**

*核查：✅*

### RG8. ⚪ 检索策略：向量、关键词、混合

三种检索方式各有盲区：

**向量检索**：懂语义，但精确匹配弱（搜"错误码 0x80070005"可能搜不到）
**关键词检索**：精确匹配强，但不懂同义词
**混合检索**：两者都跑，结果融合（RRF 重排序）——生产标配

技术文档、代码、错误码类知识库，混合检索是必选项。

*核查：✅*

### RG9. ⚪ top_k：给模型几条参考资料

检索出 top_k 条资料给模型，k 怎么选？

太小（k=1-3）：漏掉关键信息的风险大。太大（k=20）：噪音淹没重点，token 也贵。

经验起点：**k=5 + Reranker 精排**。配合"资料相关性分数过滤"（低于阈值的丢弃），宁可少而准，不要多而杂。

*核查：✅*

### RG10. ⚪ Reranker：检索精排的一 smaller 步

向量检索是"粗排"（快但糙），**Reranker 是"精排"**（慢但准）：用交叉编码器逐条细算问题和文档的相关性。

流程：向量检索 top 20 → Reranker 精排 → 取 top 5 给模型。

多花几百毫秒，命中率提升显著——RAG 提效清单里性价比最高的一个组件。

*核查：✅*

### RG11. ⚪ 查询改写：用户的问法 ≠ 检索的问法

用户问"这个东西多少钱"——知识库里写的是"产品定价策略"。字面不匹配，检索就 miss。

解法：**查询改写**——用 LLM 把用户口语改写成检索友好的表达（提取关键词、扩展同义词、拆解复杂问题）。

这一步加上后，检索命中率普遍提升 20-40%。RAG 里最被低估的组件。

*核查：⚠️ 提升数字为实践观察。常青。*

### RG12. ⚪ 多轮对话检索：先把指代说清楚

多轮对话的 RAG 有个特有问题：用户第二句问"那它多少钱呢？"——"它"是谁？

解法：**查询改写先做指代消解**（结合对话历史，把"它"还原成具体对象，再拿去检索）。

不做这步，多轮对话的 RAG 基本不可用——检索拿到的是"那它多少钱呢"这种废查询。

*核查：✅*

### RG13. ⚪ 结构化数据的 RAG：表格走 SQL 路线

知识库里大量内容是表格（价格表、规格表、统计报表）？向量检索对表格效果差。

解法：**表格走 SQL 路线**——用 Text-to-SQL 把自然语言变成查询，精准取数。

混合知识库的正确架构：文档走向量检索，表格走 SQL，路由层判断问题该走哪条路。

*核查：✅*

### RG14. ⚪ RAG 评测：两个必须盯的指标

RAG 评测盯两个指标：**检索命中率**（正确资料有没有被找回来）、**回答忠实度**（回答是否忠于检索到的资料，有没有自由发挥）。

工具：RAGAS 一类框架自动评测。没有这两个指标的 RAG，效果好坏全靠体感——体感是靠不住的。

*核查：✅*

### RG15. ⚪ 幻觉治理：回答必须带引用

RAG 治幻觉的最后一道防线：**回答必须标注引用来源**（"根据《XX 文档》第 3 节……"）。

实现：提示词强制要求 + 生成后校验（回答里的关键论断能在检索资料里找到对应）+ 找不到就回"资料中未找到"。

带引用的 RAG，用户敢用；不带引用的 RAG，用户用一次就走了。

*核查：✅*

### RG16. ⚪ 数据更新管道：知识库的新鲜度

知识库的致命伤是过时：上周的价格、旧版的政策。数据更新管道三问：

**更新频率**（每天/每周同步？）、**更新方式**（全量重建还是增量入）、**删除机制**（作废的文档有没有从库里删掉）。

"加了新文档忘了删旧文档"是 RAG 回答自相矛盾的头号原因。

*核查：✅*

### RG17. ⚪ 权限过滤：谁能检索什么

企业 RAG 的必备能力：**权限过滤**——财务部的人检索不到 HR 的薪酬文档。

实现：文档入库时打权限标签，检索时按用户身份过滤（在向量检索的过滤条件里，不是检索完再删）。

权限做在检索后而不是检索时，是安全事故的常见来源——检索本身就会把内容送进模型上下文。

*核查：✅*

### RG18. ⚪ 成本优化：缓存与路由

RAG 的成本优化三板斧：**缓存**（高频相同问题直接返回缓存答案）、**路由**（简单问题用小模型，复杂问题才上大模型）、**精简上下文**（Reranker 后只给 3-5 条最相关的，别把 20 条全塞进去）。

三板斧下来，成本通常能砍 60-80%，效果不掉。

*核查：✅*

### RG19. ⚪ 为什么你的 RAG 像人工智障：失败案例复盘

典型的"人工智障 RAG"复盘：用户问"退货流程"，系统检索到"退货保险产品介绍"（向量相似但语义完全不同）→ 模型拿着错误资料一本正经回答。

病灶三连：文档切分切烂了 + 没有查询改写 + 没有 Reranker。

对照本系列 RG4/RG11/RG10 逐个修——修完的系统和修之前的，是两个产品。

*核查：✅*

### RG20. ⚪ 进阶路线：从朴素 RAG 到 Agentic RAG

朴素 RAG 之上还有三条进阶路线：

**HyDE**（让模型先生成假设答案，再用它去检索——以答找文）、**GraphRAG**（知识图谱结构化，擅长多跳关系问题）、**Agentic RAG**（让 Agent 决定：要不要检索、检索什么、检索几轮、够不够回答）。

路线选择：朴素 RAG 覆盖 80% 场景，先跑通朴素版，遇到真实瓶颈再上进阶——**别用架构炫技替代问题解决。**

*核查：✅*
# RAG 全链路系列 · 进阶篇（RG21–RG40，9/28，未发布）

### RG21. ⚪ GraphRAG：知识图谱版 RAG

GraphRAG 的思路：把文档抽成**实体和关系的知识图谱**，检索时沿着关系路径找答案。

强项：多跳问题（"A 公司的 CEO 投资过哪些 B 领域的公司？"——需要两跳推理）——朴素 RAG 在多跳问题上几乎必败。

代价：图谱构建贵、维护重。适合知识关系复杂且稳定的场景（企业合规、情报分析），不适合时效性内容。

*核查：✅*

### RG22. ⚪ HyDE：用"假答案"找真文档

HyDE 的反直觉思路：用户提问后，**先让模型生成一个假设答案**，再用这个假设答案去做向量检索——以答找文。

原理：答案和文档的"语义距离"，比问题和文档的近——问题问的是"为什么"，文档写的是"因为"。

代价：多一次 LLM 调用（慢+贵）。适合检索命中率卡住的小知识库，先测提升再决定上不上。

*核查：✅*

### RG23. ⚪ 多模态 RAG：图片和表格也能检索

多模态 RAG 的两种路线：**图片描述化**（用 VLM 给每张图生成描述文本，入库检索，命中后把原图给模型）和**多模态 embedding**（图文统一向量空间）。

表格的特殊处理：表格转 Markdown 入库 + 附带原始表格引用——纯文本化表格是 RAG 效果差的常见元凶。

*核查：✅*

### RG24. ⚪ Agentic RAG：让 Agent 决定检索策略

Agentic RAG：把"要不要检索、检索什么、检索几轮、够不够回答"**交给一个 Agent 决定**，而不是固定流水线。

流程：Agent 收到问题 → 判断是否需要检索 → 生成检索词 → 评估结果够不够 → 不够就改写重试或拆子问题 → 够了才生成回答。

代价：多几轮 LLM 调用（慢+贵）。收益：复杂问题的成功率大幅提升。适合"问题五花八门"的场景，不适合"问题模式固定"的场景。

*核查：✅*

### RG25. ⚪ 企业级 RAG 架构全景

企业级 RAG 的完整分层，一图看懂：

**接入层**（文档管道：解析/清洗/分块/权限标签）→ **索引层**（embedding + 向量库 + 关键词索引）→ **检索层**（混合检索 + 改写 + Reranker + 权限过滤）→ **生成层**（提示词模板 + 引用强制）→ **评测层**（命中率 + 忠实度 + bad case 回流）。

每一层都是独立可优化的模块——别把它当"一个工具"，它是五个系统。

*核查：✅*

### RG26. ⚪ 流式输出与引用定位

用户体验的两个细节：**流式输出**（打字机效果，首字延迟 <2 秒的体感完全不同）和**引用定位**（回答里的每句话标注来源，点击跳原文位置）。

引用定位的实现：检索时记录每块的原文位置（页码/段落），生成后把论断和来源块对齐。

这两样是"演示级 RAG"和"产品级 RAG"的分水岭。

*核查：✅*

### RG27. ⚪ 长文档 RAG：整本书怎么处理

一本 300 页的手册进 RAG 的策略：**两层索引**——章级摘要（粗检索，定位到章）+ 段落级块（细检索，定位到段）。

先粗后细的两跳检索，比一口气切 2000 个小块的效果好：粗层保证相关性，细层保证精度。

配合"目录注入"（把书的目录给模型当地图），长文档问答的可用性质变。

*核查：✅*

### RG28. ⚪ 实时数据 RAG：新闻流的特殊处理

新闻流 RAG 和文档 RAG 的区别：**时效性是第一维度**——昨天的新闻权重必须低于今天的。

处理：入库时打时间戳 + 检索时时间衰减加权 + 旧闻定期归档（从主索引移出）。

新闻类 RAG 的用户预期是"最新"，一条过时信息混进来，整个产品的可信度归零。

*核查：✅*

### RG29. ⚪ 中文 RAG 的特殊性

中文 RAG 的三个坑：**分词歧义**（中文没空格，切块容易切破语义）、**Embedding 模型的中文能力差异大**（必须实测）、**混合检索里 BM25 的中文分词器要选好**（jieba 等的分词质量直接影响关键词检索）。

中文场景的 embedding 选型，务必用中文测试集实测——英文榜单第一的模型，中文可能排在十名开外。

*核查：✅*

### RG30. ⚪ 代码库 RAG：代码问答的特殊设计

代码库 RAG 和文档 RAG 的区别：**代码的结构就是语义**——按函数/类切分（不按行数）、保留调用关系、路径和导入信息一起入索引。

检索 query 的特殊性：开发者问"哪里处理了 token 过期"，需要语义 + 符号混合检索。

代码库 RAG 做好了，是开发团队见效最快的 AI 应用——新人 onboarding 时间砍半。

*核查：✅*

### RG31. ⚪ 客服 RAG 实战：从 0 到上线

客服 RAG 的落地清单：知识库来源（产品文档 + 历史客服对话 + FAQ）、权限分层（普通用户/ VIP/内部）、敏感边界（退款承诺类必须转人工）、回复模板（语气统一）。

上线节奏：先内部试用两周（客服自己用）→ 收集 bad case 修复 → 再对客开放 10% 流量 → 全量。

跳过内部试用直接对客，是客服 RAG 翻车的标准剧本。

*核查：✅*

### RG32. ⚪ 法律 RAG 实战：准确率是生命线

法律 RAG 的特殊性：**一个错误的法条引用，比没有回答严重一百倍**。

设计要点：法条库带版本和时效（废止法条必须标记）、回答强制引用原文条款、检索半径收紧（只给最高置信的条文）、免责与人工复核提示常驻。

法律场景的 RAG，宁可不回答，也不能答错。

*核查：✅*

### RG33. ⚪ RAG 的缓存层：高频问题的免烧方案

RAG 的成本大头是每次的检索+生成。缓存层三级：

**精确缓存**（完全相同的问题，直接返回）、**语义缓存**（语义相近的问题，返回缓存答案——用 embedding 判断相似度 >0.95）、**片段缓存**（检索结果缓存，只重跑生成）。

客服/FAQ 类场景命中率极高——缓存命中率 30% 就意味着成本砍三成。

*核查：✅*

### RG34. ⚪ 评测自动化流水线

RAG 评测的自动化流水线：**固定评测集**（100+ 真实问题 + 金标准答案）→ 每次改动自动跑 → 输出检索命中率/忠实度/引用准确率三指标对比 → 回退告警。

挂在 CI 里：改分块策略、换 embedding 模型、调提示词——任何改动先过评测流水线再上线。

"改了感觉更好"在 RAG 里是最危险的句式。

*核查：✅*

### RG35. ⚪ RAG 安全：注入与越权

RAG 的两大安全面：**知识库投毒**（有人往知识库塞恶意文档，污染所有回答——文档来源要审计）和**检索越权**（用户通过精心构造的问题，套出权限外的内容——权限过滤必须在检索层做）。

第三种：**跨文档推理泄露**——单篇文档无害，两篇组合起来泄露敏感信息。这类问题只有红队测试能发现。

*核查：✅*

### RG36. ⚪ 多知识库路由：一个入口，多个库

企业里知识库不止一个：产品文档库、内部制度库、技术文档库。**路由层**判断问题属于哪个库，分别检索。

实现：轻量路由（小模型分类问题归属）+ 各库独立检索 + 结果融合。

路由错库 = 检索质量归零——路由层的准确率要单独评测（这本身又是一个分类任务）。

*核查：✅*

### RG37. ⚪ RAG 与微调的组合拳

RAG 和微调不是二选一，是组合拳：**微调管"怎么答"**（口径、格式、风格统一），**RAG 管"答什么"**（最新、最准的内容）。

组合架构：RAG 检索内容 + 微调模型按企业口径组织输出。

只用 RAG：回答风格飘；只用微调：内容会过时。组合才是企业级形态。

*核查：✅*

### RG38. ⚪ 成本与延迟的平衡艺术

RAG 的每个优化都有代价：Reranker 提准确率但加延迟、混合检索提命中率但双倍检索成本、大 k 提召回但烧 token。

平衡的艺术：**按场景分配预算**——客服场景要快（砍 Reranker，用缓存）、法律场景要准（全上，慢点没事）、内部场景要省（全砍）。

没有最优配置，只有场景最优配置。

*核查：✅*

POC（一周做的演示）到生产系统之间，常见的十二道坎：文档解析的质量、权限过滤、增量更新、评测流水线、引用定位、缓存、流式输出、多库路由、安全加固、成本控制、bad case 处理、用户反馈闭环。

# RAG 全链路系列 · 第三批（RG41–RG65，9/29，未发布）

### RG41. ⚪ 元数据过滤：检索的精准手术刀

向量检索加**元数据过滤**（metadata filtering）：文档入库时打标签（来源/日期/部门/类型），检索时按标签先过滤再算相似度。

效果：在 10 万文档里只搜最近 30 天的、只搜某个部门的——**过滤把检索从大海捞针变成鱼塘捞鱼**。

元数据的设计比过滤本身重要：入库时没打好标签，检索时就无从过滤。

*核查：✅*

### RG42. ⚪ 混合检索的权重调优

混合检索（向量+关键词）的权重调优：**RRF（倒数排名融合）**是免调参的默认解，但加权融合（向量 0.7 + 关键词 0.3）可以更贴合场景。

调优方法：用评测集测不同权重下的命中率——**关键词命中多的场景调高关键词权重**（技术文档/代码），语义场景调高向量权重。

*核查：✅*

### RG43. ⚪ 多路召回的架构

进阶 RAG 的多路召回架构：一次查询，**四路并发**——向量检索 + 关键词检索 + 元数据过滤 + 图谱查询，结果融合后统一排序。

多路召回解决单路盲区：向量懂语义不懂精确、关键词懂精确不懂语义、图谱懂关系。

架构复杂度 ×4，命中率提升 30-50%——**企业级 RAG 的标配，个人级可先做两路。**

*核查：✅*

### RG44. ⚪ 查询分解：复杂问题拆成简单查询

用户问"A 公司和 B 公司合作过的项目里，哪些用了 C 技术？"——一步检索找不到答案。

**查询分解**：让 LLM 把复杂问题拆成子查询（"A 和 B 的合作项目" + "项目中用 C 技术的"）→ 分别检索 → 合并推理。

Agentic RAG 的核心能力之一——复杂问答的分水岭。

*核查：✅*

### RG45. ⚪ 检索结果的重排策略

多路召回的结果怎么合并排序？策略：**去重**（同一文档多路命中只留最高分）→ **加权重排**（按场景配权重）→ **Reranker 精排**（交叉编码器重算）→ **top_k 截断**。

重排的评测：用真实问题集对比重排前后的命中率——**重排是所有 RAG 优化里 ROI 最确定的一环。**

*核查：✅*

### RG46. ⚪ Embedding 微调实战：领域适配

通用 embedding 在垂直领域"认识词不认识意思"——领域 embedding 微调的三步：

**构造三元组**（领域问题 + 正例文档 + 负例文档）、**选基座**（BGE/GTE 开源系）、**对比学习训练**（几百到几千个三元组见效）。

领域 embedding 微调后，检索命中率普遍提升 15-30%——**RAG 优化的深水区，但值得。**

*核查：✅*

### RG47. ⚪ 文档解析工具链：PDF 的战争

RAG 的第一道坎是文档解析：**PDF 的表格、多栏、扫描件**是三大恶仗。

工具链：pymupdf（文本层提取）、unstructured（结构感知）、OCR（扫描件，如 PaddleOCR）、表格专用（camelot/tabula）。

实战建议：**按文档类型分流**——文本层好的走直提、扫描件走 OCR、表格走专用解析。解析质量决定 RAG 上限。

*核查：✅*

### RG48. ⚪ 增量索引：知识库更新的正确姿势

知识库更新的增量索引流程：**变更检测**（源文档的 hash/时间戳对比）→ **增量删除**（旧文档的向量从库里删）→ **增量入库**（只嵌入新内容）→ **版本标记**。

全量重建 vs 增量更新的选择：文档 <1 万全量也无妨；更大就必须增量——**重建一次的成本，是增量设计的十倍。**

*核查：✅*

### RG49. ⚪ RAG 的成本解剖

RAG 一次查询的真实成本构成：**embedding 计算**（问题向量化，便宜）、**检索**（向量库查询，几乎免费）、**Reranker**（贵一点）、**LLM 生成**（大头，与检索文档长度正相关）。

成本优化第一刀：**控制给 LLM 的文档总长度**（top_k × 块大小的乘积）——这个数字减半，生成成本减半。

*核查：✅*

### RG50. ⚪ 上下文压缩：检索结果的瘦身术

检索回来的 5 段文档，每段 800 字 = 4000 token 进上下文——**其中可能只有 20% 与问题直接相关**。

上下文压缩：用小模型把每段压缩成与问题相关的摘录（"只保留与 X 相关的句子"）——token 减 70%，答案质量不掉。

**压缩发生在喂给大模型之前**——大模型的上下文留给推理，不留给原文。

*核查：✅*

### RG51. ⚪ RAG 的引用设计：行内引用 vs 文末引用

引用设计的两种风格：**行内引用**（每句话后面跟 [1][2]——可信度强、阅读打断）vs **文末引用**（全文末尾列来源——流畅但用户不看）。

折中方案：**关键论断行内标注 + 文末完整来源列表**。

带引用的 RAG 是合规和信任的刚需——引用设计决定用户敢不敢信。

*核查：✅*

### RG52. ⚪ 多轮 RAG 的对话管理

多轮对话中的 RAG 状态管理：**检索历史**（避免重复检索同样的内容）、**对话摘要**（长对话压缩后仍能做指代消解）、**已用来源追踪**（同一来源不重复注入）。

多轮 RAG 的复杂度是单轮的三倍——但用户一旦多轮追问，单轮设计的 RAG 立刻露馅。

*核查：✅*

### RG53. ⚪ RAG 的 A/B 测试框架

RAG 改动的 A/B 测试框架：**同一组真实问题 → 分别走新旧配置 → 自动对比三指标**（检索命中率/忠实度/引用准确率）。

改动哪些要先测：分块策略、embedding 模型、Reranker 开关、top_k、提示词。

**每个改动都测**——RAG 的参数间有隐秘的相互作用，"感觉更好"经常是错觉。

*核查：✅*

### RG54. ⚪ 冷启动知识库：从 0 到可用的最快路径

冷启动知识库的最快路径五步：**选一个解析器**（unstructured）、**粗糙分块**（500 字+10% 重叠）、**通用 embedding**（BGE）、**朴素检索**（向量 top5）、**简单提示词**（带引用要求）。

全程一天。**先跑通再优化**——90% 的 RAG 优化决策，需要先有基线才有意义。

*核查：✅*

### RG55. ⚪ RAG 失败案例五大典型

RAG 的五大典型失败：**检索 miss**（相关文档在库里但没搜到——查分块和 embedding）、**检索到但没用**（提示词没引导模型基于资料回答）、**过时信息**（知识库没更新管道）、**权限泄露**（检索没做权限过滤）、**上下文爆炸**（塞了太多低相关文档）。

每个失败对应本系列的一篇——**失败模式识别是调优的第一步。**

*核查：✅*

### RG56. ⚪ RAG 产品的用户反馈闭环

RAG 产品的反馈闭环设计：**每次回答带 👍/👎**→ 👎 时追问"哪里不对"（检索不到？答案错？）→ 反馈进 bad case 库 → 按模式修复（检索问题调检索，生成问题调提示词）。

用户反馈是 RAG 优化的免费指南针——**用户的 👎 比你的评测集更接近真实。**

*核查：✅*

### RG57. ⚪ 企业 RAG 的数据源接入清单

企业知识库的数据源接入优先级：**Wiki/文档平台**（Confluence/飞书文档——结构好）→ **工单系统**（历史问答金矿）→ **邮件归档**（量大但脏）→ **聊天记录**（敏感，慎入）。

接入顺序：先结构好的，后脏数据——**每一类源一个解析适配器 + 独立的更新频率。**

*核查：✅*

### RG58. ⚪ RAG 的响应速度优化

RAG 响应速度的优化清单：**向量库索引类型**（HNSW vs 暴力——数据大了必须 HNSW）、**Reranker 模型换小**（cross-encoder 换轻量版）、**检索结果并行生成**（流式返回首块）、**缓存**（高频问题命中）。

延迟的预算分配：检索 <500ms、Rerank <300ms、生成首字 <1s——**每一段都有独立的优化空间。**

*核查：✅*

### RG59. ⚪ RAG 的多语言挑战

多语言知识库的 RAG 挑战：**跨语言检索**（中文问题搜英文文档——需要多语言 embedding 或翻译层）、**混合语言分块**（中英混排文档的切分）、**各语言的知识更新同步**。

解法：多语言 embedding 模型（BGE-M3 类）+ 查询翻译层 + 按语言分库路由。

*核查：✅*

### RG60. ⚪ RAG 与 Agent 的融合点

RAG 和 Agent 的融合形态：**Agent 决定检索策略**（检索什么、从哪个库、要不要多轮）——RAG 从"固定流水线"变成"Agent 的一个工具"。

融合的触发条件：知识库多个、问题复杂多变、需要多轮检索。

朴素 RAG 先跑通，Agent RAG 是进阶牌——**顺序别反。**

*核查：✅*

### RG61. ⚪ 评测数据集的冷启动

RAG 评测集的冷构建：**从真实用户问题起步**（哪怕只有 30 个）+ **金标准答案人工写** + **按难度分层**。

没有真实用户问题时的替代：让 LLM 从文档里生成候选问题——**生成的问题要人工过一遍**（LLM 生成的偏简单）。

评测集从第一天就开始攒——**它是 RAG 持续优化的唯一度量衡。**

*核查：✅*

### RG62. ⚪ RAG 的监控仪表盘

RAG 上线后的监控仪表盘六项：**日查询量**、**检索命中率**（抽样自动评测）、**平均响应时间**、**无答案率**（多少问题检索不到相关内容）、**用户反馈分布**（👍/👎）、**知识库新鲜度**（最后更新时间）。

"无答案率"是最容易被忽略的黄金指标——**它直接告诉你知识库缺什么。**

*核查：✅*

### RG63. ⚪ RAG 的失败重试设计

检索失败的优雅处理：**第一轮检索无结果 → 查询改写重试**（同义词扩展）→ **仍无结果 → 降低相关度阈值再试** → **还没有 → 诚实告知"知识库中没有相关内容"并建议提问方式**。

**绝不假装回答**——检索失败时的"硬编"是 RAG 最恶劣的失败模式。

*核查：✅*

### RG64. ⚪ RAG 的选型速查：框架与库

RAG 技术栈速查：**编排框架**（LlamaIndex——RAG 优先；LangChain——全家桶）、**向量库**（Chroma 起步 / Milvus / pgvector）、**Embedding**（BGE 中文 / OpenAI 通用）、**Reranker**（BGE-reranker / Cohere）、**评测**（RAGAS）。

选型原则：**每个组件选"你能 debug 的"**——出问题时能排查比功能全重要。

# RAG 全链路系列 · 第四批（RG66–RG90，9/29，未发布）

### RG66. ⚪ RAG 的语义分块：不是按字数，是按意思

语义分块（Semantic Chunking）：**用 embedding 相似度检测语义边界**——相邻句子的相似度下降超过阈值 = 语义边界 = 切分点。

效果：比固定字数切分的检索命中率高 15-25%。

代价：多一轮 embedding 计算（入库变慢）。

**入库慢一点换检索准一点——值得。**

*核查：✅*

### RG67. ⚪ RAG 的父文档检索：小块检索，大块回答

父文档检索（Parent Document Retrieval）：**用小块（200 字）做检索（精确），命中后返回大块（2000 字，上下文丰富）**。

原理：小块匹配更精准（关键词密度高），但大块给模型的上下文更完整（不会断章取义）。

架构：**索引用小块 + 返回用父块**——两全其美。

*核查：✅*

### RG68. ⚪ RAG 的多模态扩展：图片也进知识库

多模态 RAG：**图片/表格/图表也入库**——

路线一：VLM 给图片生成描述文本 → 文本入库（图片的可搜索性）
路线二：多模态 embedding（图文统一向量空间）

实用场景：产品手册里的截图、财报里的图表、PPT 里的图示。

*核查：✅*

### RG69. ⚪ RAG 的查询路由：一个问题走哪条路

多知识库的路由策略：**LLM 分类器**（判断问题属于哪个知识库）→ 路由到对应库检索 → 结果合并。

路由的准确率决定 RAG 的下限：路由错了 = 检索错库 = 答非所问。

路由的评测：**路由准确率单独统计**——路由错了比检索不到更糟（给用户错误的答案）。

*核查：✅*

### RG70. ⚪ RAG 的重排序：Cross-Encoder vs Bi-Encoder

检索的两阶段：**Bi-Encoder**（问题+文档分别编码，快但粗）→ **Cross-Encoder**（问题+文档一起编码，慢但准）。

两阶段的分工：Bi-Encoder 召回 top 20 → Cross-Encoder 精排 → top 5 给模型。

Cross-Encoder 的提升：命中率 +15-30%（比纯向量检索）。

*核查：✅*

### RG71. ⚪ RAG 的混合检索实现：BM25 + 向量

混合检索的实现：**BM25（关键词匹配）+ 向量检索（语义匹配）→ RRF 融合**。

BM25 的优势：精确匹配（错误码/产品型号/人名）——向量检索的盲区。
向量检索的优势：语义理解（"怎么退货"≈"退换货流程"）。

**BM25 + 向量 > 任一单独使用**——已有多个论文和产品验证。

*核查：✅*

### RG72. ⚪ RAG 的上下文排序：相关性 ≠ 位置

检索结果的排列影响生成质量：**最相关的放最后**（靠近生成位置——recency bias）。

排序策略：**相关度排序 → 反转**（最高相关的放最后）——利用模型的 recency bias。

进阶：**" lost in the middle" 测试**（把关键信息放在上下文的不同位置，测命中率）——找到你的模型的最佳位置。

*核查：✅*

### RG73. ⚪ RAG 的自查询：让模型自己加过滤条件

Self-query：**让模型从用户问题中自动提取元数据过滤条件**——

用户问"最近 30 天的价格超过 100 的产品"→ LLM 提取（日期范围：最近 30 天、价格：>100）→ 检索时加元数据过滤。

价值：**用户的自然语言 → 结构化的检索条件**——不用要求用户"按格式提问"。

*核查：✅*

### RG74. ⚪ RAG 的文档更新：增量 vs 全量的决策

知识库更新的决策树：**变更文档数 <10%** → 增量更新（只处理变化的）→ **变更 >50%** → 全量重建（增量维护成本更高）→ **变更 10-50%** → 增量 + 定期全量校验。

增量更新的坑：**删了源文档但忘了删向量**——需要文档 ID 关联和级联删除。

*核查：✅*

### RG75. ⚪ RAG 的权限过滤：检索层的权限

RAG 权限过滤的实现：**文档入库时打权限标签**（部门/级别/用户组）→ **检索时按用户权限过滤**（在检索层过滤，不在展示层）。

检索层过滤 > 展示层过滤的原因：**检索时过滤 = 敏感内容根本不进上下文**；展示层过滤 = 内容已经进上下文了，用户可能通过提示词注入绕过展示层过滤。

*核查：✅*

### RG76. ⚪ RAG 的多租户：知识库隔离

多租户 RAG 的隔离设计：**租户级向量库**（每个租户独立的 collection）→ **租户级 embedding**（各租户可以选不同模型）→ **租户级配置**（分块策略/检索参数独立）。

隔离的必要性：**租户 A 的文档绝不能出现在租户 B 的检索结果中**——数据隔离是产品级的信任基础。

*核查：✅*

### RG77. ⚪ RAG 的缓存设计：三级缓存

RAG 的三级缓存：**L1 查询缓存**（完全相同的问题 → 直接返回上次答案）、**L2 语义缓存**（语义相近的问题 → 返回缓存答案 + 标注"相似问题"）、**L3 文档缓存**（检索到的文档缓存，跳过重复的 embedding 计算）。

三级缓存的命中率：客服场景 30-50%、文档问答 20-30%——**命中率 30% = 成本降 30%。**

*核查：✅*
