# MCP 与插件生态系列 · 草稿（MC1–MC30，9/28，未发布）

### MC1. ⚪ MCP 一文讲透：AI 世界的 USB 标准

MCP（Model Context Protocol，Anthropic 开源协议）解决一个根本问题：**每个 AI 应用接每个工具，都要写一次专用胶水代码——M×N 的集成地狱**。

MCP 把它变成 M+N：工具方实现一次 MCP Server，所有支持 MCP 的应用都能用；应用方支持一次 MCP Client，所有 MCP 工具都能接。

类比：USB 之前，每个外设一个专用接口；USB 之后，一个口插所有。MCP 就是 AI 工具的 USB。

*核查：✅*

### MC2. ⚪ MCP 的架构：Host、Client、Server

MCP 的三个角色：

**Host**：AI 应用本体（Claude Desktop、Cursor、你的 Agent）——用户在这里交互。
**Client**：Host 内部维护的连接器（每个 Server 一条连接，1:1）。
**Server**：提供能力的独立服务（文件系统/数据库/GitHub/Slack——可以是任何人写的任何程序）。

数据流：用户在 Host 提问 → Host 的模型决定用哪个 Server 的哪个能力 → Client 向 Server 发请求 → 结果回到模型。

**关键安全认知**：Server 是第三方程序——你装的每个 Server，都是在给 Agent 增加一个有权限的"员工"。

*核查：✅*

### MC3. ⚪ MCP 的三大原语：Tools、Resources、Prompts

MCP Server 能提供三种东西（原语）：

**Tools（工具）**：可执行的函数——"创建工单""查询数据库"。模型**主动决定**何时调用。
**Resources（资源）**：可读取的数据——文件内容、配置、文档。应用**按需取用**，作为上下文注入。
**Prompts（提示词模板）**：预制的提示词模板——用户可以主动选择使用。

三者的分野：Tool 是"动作"，Resource 是"材料"，Prompt 是"剧本"。一个好的 MCP Server，三样搭配着提供。

*核查：✅*

### MC4. ⚪ 第一个 MCP Server：30 行代码的最小实现

用 Python SDK 写一个最小 MCP Server（30 行）：

**导入 FastMCP → 实例化 → @mcp.tool() 装饰一个函数 → run。**

示例：一个"查询天气"的 Server——函数名 `get_weather`、参数 `city: str`、返回 JSON。写完一个命令启动，Claude Desktop 的配置文件里加一行，重启——你的自定义工具出现在 Claude 的工具列表里。

**"我的第一个自定义工具出现在大模型手里"——这个体验是 MCP 生态的入坑时刻。**

*核查：✅ FastMCP 为官方 Python SDK 的高层封装。*

### MC5. ⚪ 传输层：stdio 与 HTTP 的取舍

MCP 的两种传输方式：

**stdio**（标准输入输出）：Server 作为 Host 的子进程本地运行——快、安全（不暴露网络端口）、只能本机用。
**HTTP（SSE/Streamable HTTP）**：Server 远程运行——可远程共享、可多用户、需要处理鉴权。

选择：个人本地工具用 stdio；团队共享/云服务用 HTTP。**远程 MCP Server 的鉴权是安全设计的重点**（别把没鉴权的 Server 挂公网）。

*核查：✅*

### MC6. ⚪ 官方 SDK 生态：TypeScript 与 Python 双雄

MCP 官方 SDK 两大门派：

**TypeScript SDK**：前端/Node 生态的开发者主场。
**Python SDK**（含 FastMCP 高层封装）：数据/AI 工程师主场。

两个 SDK 的抽象类似（Server/Tool/Resource 的概念一致）——会一个，另一个半天上手。

社区还有 Go/Rust/Java/Kotlin 等社区版 SDK——协议是开放的，语言不是门槛。

*核查：✅*

### MC7. ⚪ MCP 的安全模型：信任边界在哪

MCP 的安全模型的核心问题：**Host 信任 Server 吗？**

风险清单：恶意 Server（窃取数据/诱导有害行为）、合法 Server 的漏洞（间接注入——Server 返回的内容里藏指令）、权限过宽（文件系统 Server 拿到了全盘权限）。

最佳实践：Server 来源审计（用官方/知名来源的）、最小权限（文件系统 Server 只挂载需要的目录）、用户确认机制（工具调用前 Host 应提示用户）、输出隔离（Server 返回的内容按数据处理）。

*核查：✅*

### MC8. ⚪ 生态盘点：最有用的 MCP Server 们

MCP 生态里最常用的 Server 盘点：

**文件系统**（读写本地文件）、**GitHub/GitLab**（仓库操作/PR 管理）、**数据库**（Postgres/MySQL 的查询）、**浏览器**（Puppeteer/Playwright 控制——Agent 能上网了）、**Slack/飞书**（消息收发）、**搜索引擎**（Brave/Exa）、**内存/知识图谱**（Agent 的长期记忆）。

生态的规律：**每个 MCP Server 都是把"一个传统软件的能力"暴露给 AI**——你常用的软件，大概率已有社区 Server。

*核查：✅ 生态动态变化，以官方 registry 为准。*

### MC9. ⚪ 企业评估 MCP Server：安全审计清单

企业引入第三方 MCP Server 的审计清单：**来源**（谁开发的、开源吗、star 数和维护活跃度）、**权限**（它要求访问什么——一个天气 Server 要读你的文件系统 = 红灯）、**传输**（本地 stdio 还是远程 HTTP，数据流向哪里）、**依赖**（它的依赖链安全吗）、**行为**（跑起来后实际访问了什么——监控验证）。

清单的本质：**你装的不是插件，是替你执行操作的程序。**

*核查：✅*

### MC10. ⚪ 自研 vs 现成：什么时候自己写 MCP Server

自己写 MCP Server 的三个信号：**内部系统没有现成 Server**（你们的 ERP/CRM——自己写一个，把内部能力暴露给 AI）、**现成的权限模型不匹配**（需要对接你们的 IAM）、**数据敏感**（不能经过第三方 Server 的中转）。

不需要自己写的：通用能力（搜索/文件/GitHub——社区版够用）。

自研的成本：一个熟练开发者 1-3 天（用 SDK 的画）——**内部系统的 AI 化，MCP 是当前最短的路。**

*核查：✅*

### MC11. ⚪ MCP 与函数调用：互补而不是竞争

常见困惑：模型有 Function Calling 了，MCP 是重复造轮子吗？

不是，分工不同：**Function Calling 是模型的能力**（模型输出结构化的调用意图）；**MCP 是工具的分发协议**（工具从哪来、怎么连、怎么发现）。

组合关系：模型的 function calling 输出"要调 MCP 工具 X"，MCP Client 负责真正执行。

一句话：**Function Calling 是手，MCP 是工具箱。**

*核查：✅*

### MC12. ⚪ Resources：上下文注入的正确姿势

MCP Resources 的正确用法：**把大而稳定的内容作为 Resource 提供**（API 文档、配置说明、数据 schema），Host 按需读取注入上下文。

设计要点：Resource 的粒度（整个文件还是按节提供——大文件提供分段列表）、更新通知（内容变了通知 Host）、**别把敏感数据做成 Resource**（Resource 会被注入上下文——权限模型要清楚）。

Resource vs Tool 的判断：只读不改 → Resource；有副作用 → Tool。

*核查：✅*

### MC13. ⚪ Prompts 原语：团队提示词的分发机制

MCP 的 Prompts 原语被低估了：它是**团队提示词的分发机制**——把团队验证过的最佳提示词做成 MCP Server 的 Prompts，全员通过 Host 一键调用。

场景：客服团队的回复模板、分析师的分析框架、程序员的 code review 清单。

价值：**提示词的版本管理和分发**，通过 MCP 协议标准化了——团队提示词工程（呼应 PE25）的基建。

*核查：✅*

### MC14. ⚪ MCP Server 的测试

MCP Server 的测试三层：

**单元**（每个 tool 的输入输出正确性）、**集成**（通过 MCP Client 走真实协议调用）、**端到端**（在真实 Host 里让模型"自然地"选择调用——模型的选择逻辑也是被测对象）。

易漏的测试点：错误路径（参数错、服务挂了时返回什么）、并发（多个请求同时来）、大返回值（返回 1MB 数据时上下文炸不炸）。

*核查：✅*

### MC15. ⚪ 版本与兼容性：协议演进的管理

MCP 协议在快速演进（版本更新、新能力），兼容性管理要点：

**协议版本协商**（Client 和 Server 握手时确认版本）、**向后兼容**（加字段可以，删字段要谨慎）、**能力声明**（Server 声明自己支持什么，Host 按需使用）。

用户的实用建议：**锁定常用 Server 的版本**，升级前看 changelog——协议快跑期，盲升级的坑真实存在。

*核查：✅*

### MC16. ⚪ Marketplace 上架流程：从写好到发布

把 MCP Server 上架到 Marketplace（Claude 的插件目录等）的流程：**打包**（按目录规范组织）、**清单文件**（名称/描述/工具声明/权限声明）、**提交审核**（安全与质量审查）、**发布与更新**（版本管理）。

上架前的自查：描述准确吗（用户按描述决定装不装）、权限声明诚实吗（要的权限和实际用的一致）、错误处理优雅吗（挂了不能拖死 Host）。

上架 = 你的工具进入 AI 的"应用商店"分发体系。

*核查：⚠️ 各 Marketplace 的审核流程以官方文档为准。*

### MC17. ⚪ 插件的产品设计：发现、安装、信任

插件生态的产品设计三要素：

**发现**（用户怎么找到你的插件——分类/搜索/推荐位）、**安装**（一键装 + 权限说明透明）、**信任**（评分/评价/开发者信誉/安全审计标识）。

类比应用商店的成熟经验：**评分和权限透明度，决定安装转化率**——用户对"要读我的文件"的 Server，比"只要一个 URL"的，多三倍的犹豫。

*核查：✅*

### MC18. ⚪ 插件的商业模式：免费、付费、订阅

MCP 插件的商业模式选项：**完全免费开源**（建立影响力——生态早期最有效）、**免费 + Pro 功能**（核心免费，高级能力收费）、**企业授权**（私有部署 + 支持，按年费）、**按调用量**（Server 云托管，按使用计费）。

生态早期的策略：**先免费攒用户，用户的需求就是付费产品的需求清单**（呼应 Agent 系列 AG16 的流水线思维）。

*核查：✅*

### MC19. ⚪ 插件的质量信号：用户怎么挑

用户挑选 MCP 插件的质量信号清单：**开发者信誉**（个人/组织/过往作品）、**维护活跃度**（最后更新时间/issue 响应）、**社区验证**（star/下载/评价）、**权限诚实度**（声明的权限和实际行为一致）、**文档质量**（README 有使用示例）。

反向信号：无人维护（最后更新一年前）、要权限一大堆却说不出为什么、没有错误处理说明。

*核查：✅*

### MC20. ⚪ 插件的权限与确认 UX

插件权限的用户确认 UX 设计（Host 的责任）：

**安装时**：声明要什么权限（"此插件可读取 ~/documents 目录"）、**调用时**：敏感工具调用前弹确认（"允许向 GitHub 创建 PR？"）、**批量授权**（信任的插件可记住授权，敏感操作仍逐次确认）。

设计哲学：**用户应该是"知情且在环"的**——全自助（危险）和全确认（烦死）之间，按操作风险分级。

*核查：✅*

### MC21. ⚪ 插件开发者社区运营

MCP 插件开发者的社区运营：**文档先行**（README 是第一道门面：安装/配置/示例齐全）、**示例丰富**（每个工具一个可跑的示例）、**响应 issues**（48 小时内的响应是社区口碑的分水岭）、**更新公告**（每次更新写 changelog）。

冷启动技巧：自己提 issue 自己答（预埋 FAQ）、在相关社区展示 demo、和 Host 应用方联动（被官方推荐一次，顶三个月推广）。

*核查：✅*

### MC22. ⚪ MCP 的局限与批评

MCP 的局限，听批评的声音：

**安全模型还在成熟**（鉴权、审计的标准化不足——远程 Server 的安全尤其被诟病）、**协议能力边界**（复杂交互——多轮 UI、流式大文件——支持还在演进）、**生态碎片化苗头**（各家 Host 的支持程度不一、扩展不统一）。

冷静的判断：MCP 赢在了**先发和 Anthropic 的推动**，但协议的竞争者（其他厂商的类似标准）和社区批评，都是它要过的坎。**用它的标准化价值，同时别把架构绑死在它身上。**

*核查：🔶 协议演进中的批评为公开讨论，评价时效性强。*

### MC23. ⚪ 竞品协议对比：A2A 与其他标准

MCP 不是唯一的协议标准：**Google 的 A2A**（Agent-to-Agent——Agent 之间互相对话的协议，和 MCP 的"Agent 连工具"互补）、各厂商的私有协议。

关系判断：MCP（Agent↔工具）和 A2A（Agent↔Agent）**解决不同层的问题**——可能长期共存甚至互补。

对开发者的策略：**跟随生态采用率**——协议的价值在于采用者数量，技术上再优雅没人用也是零。当前 MCP 的生态位最稳。

*核查：⚠️ 协议竞争格局动态变化。*

### MC24. ⚪ 企业内部的 MCP 部署

企业内部部署 MCP 的架构：**内网 MCP Server 集群**（内部系统的能力封装：ERP/CRM/HR 系统）+ **统一的 MCP 网关**（鉴权、审计、权限过滤）+ **员工的 Host 配置**（指向内网网关）。

价值：员工用自然语言操作内部系统（"帮我查上月华东区的销售数据"）——**企业 AI 化的最短路径，就是 MCP 化内部系统。**

安全要点：网关统一鉴权（Agent 的身份对应人的权限）、操作审计全覆盖。

*核查：✅*

### MC25. ⚪ MCP 调试技巧

MCP Server 开发的调试技巧：**MCP Inspector**（官方调试工具：可视化了工具列表/调用/响应）、**日志**（Server 的 stderr 输出在 Host 的日志里看）、**最小复现**（出问题时先用 Inspector 手动调用排除 Host 因素）。

高频坑：stdio 模式的 Server 别往 stdout 打印日志（stdout 是协议通道！日志走 stderr）、参数类型不匹配的静默失败、异步操作的超时。

*核查：✅*

### MC26. ⚪ 性能与成本考量

MCP Server 的性能与成本考量：

**延迟**（工具调用是串行的——每个工具几秒，多工具任务的时间线性涨）、**返回体积**（大返回值占上下文——分页/摘要/文件化三选）、**成本**（工具结果进入上下文 = 推理 token 增加）。

优化：返回值瘦身（只要关键字段）、结果缓存（幂等查询）、**工具调用批量化**（一次调用返回批量数据好过多次调用）。

*核查：✅*

### MC27. ⚪ 从 API 到 MCP 的迁移路径

已有 REST API 的团队迁移到 MCP 的路径：**包装**（写一个 MCP Server，内部调用现有 REST API——一天就能做完）、**鉴权对接**（MCP Server 的身份映射到 API 的鉴权）、**工具化裁剪**（不是每个 REST 端点都值得暴露——按 AI 任务的视角选）。

迁移的价值：API 面向开发者（要写代码），MCP 面向所有 AI 应用（自然语言就能用）——**用户群扩大了一个数量级。**

*核查：✅*

### MC28. ⚪ MCP 在 n8n / 工作流工具中的集成

MCP 与工作流自动化工具（n8n/Make）的集成：n8n 已有 MCP 相关节点（把工作流暴露为 MCP Server、或调用外部 MCP Server）。

组合玩法：**n8n 的工作流（复杂业务逻辑）封装成 MCP Server** → AI Agent 调用它 → Agent 的推理 + n8n 的执行力结合。

这打通了两个世界：Agent 的灵活性 + 工作流的可靠性——自动化的下一形态。

*核查：⚠️ n8n 的 MCP 支持为快速迭代的功能，以官方文档为准。*

### MC29. ⚪ 生态展望：MCP 的未来三年

MCP 生态三年的展望（基于当前趋势的推演）：

**标准化深化**（鉴权、审计、付费的标准方案补齐）、**企业采用**（内部系统 MCP 化成为企业 AI 化的标准动作）、**Server 经济**（优质 Server 的商业模式成型——按调用付费/企业授权）、**Host 竞争**（谁的 Host 插件体验好，谁拿走用户）。

# MCP 与插件生态系列 · 第二批（MC31–MC55，9/29，未发布）

### MC31. ⚪ MCP Server 的错误处理

MCP Server 的错误处理设计：**错误码标准化**（不是随意的字符串）、**错误信息可操作**（告诉 Agent 怎么修正）、**部分失败的处理**（批量操作中一个失败不影响其他）。

错误的设计原则：**Agent 靠错误信息自我修正**——报错写得越好，Agent 自愈能力越强。

*核查：✅*

### MC32. ⚪ MCP Server 的日志

MCP Server 的日志设计：**请求日志**（谁调了什么工具、参数是什么）、**结果日志**（返回了什么、耗时多久）、**错误日志**（出错了、为什么）。

日志的脱敏：**参数里可能有用户的敏感数据**——脱敏后再写日志。

*核查：✅*

### MC33. ⚪ MCP Server 的监控

MCP Server 的监控指标：**调用量**（每分钟多少次）、**延迟**（P50/P95/P99）、**错误率**（失败占比）、**并发数**（同时处理的请求数）。

监控的告警：**错误率 >5% → 告警**、**P95 >10s → 告警**、**调用量突增 10 倍 → 告警**（可能是被滥用）。

*核查：✅*

### MC34. ⚪ MCP Server 的性能优化

MCP Server 的性能优化：**缓存**（重复查询直接返回）、**批量**（多个请求合并处理）、**异步**（耗时操作异步化，立即返回任务 ID）、**连接池**（数据库连接复用）。

性能的目标：**P95 延迟 <3 秒**——Agent 的用户等不了更久。

*核查：✅*

### MC35. ⚪ MCP Server 的多租户

MCP Server 的多租户设计：**租户隔离**（租户 A 的数据不能给租户 B）、**配额管理**（每个租户的调用限制）、**计费**（按调用量计费）。

多租户的架构：**共享 Server + 租户 ID 隔离**（轻量）vs **独立 Server 实例**（重量级但完全隔离）。

*核查：✅*

### MC36. ⚪ MCP Server 的认证：OAuth / API Key / 自定义

MCP Server 的认证方式：**API Key**（最简单——适合个人）、**OAuth 2.0**（标准——适合企业）、**自定义 token**（灵活但要自己管理）。

认证的原则：**远程 Server 必须认证**（本地 stdio 可以不认证——因为不暴露网络端口）。

*核查：✅*

### MC37. ⚪ MCP Server 的速率限制

MCP Server 的速率限制：**按 Client 限**（每个连接的限制）、**按工具限**（不同工具不同限制——搜索可以频繁，数据库写入要限）、**全局限**（整个 Server 的总量限制）。

限流的算法：**令牌桶**（允许突发）、**滑动窗口**（平滑限制）。

*核查：✅*

### MC38. ⚪ MCP Server 的数据隐私

MCP Server 处理的数据隐私：**不存储不必要的数据**（Agent 传来的参数处理完就丢）、**日志脱敏**（参数里可能有 PII）、**传输加密**（远程 Server 必须 TLS）。

隐私的原则：**Server 是处理数据的管道，不是数据的仓库**——处理完不留。

*核查：✅*

### MC39. ⚪ MCP Server 的测试框架

MCP Server 的测试框架三层：**单元**（每个 tool 的输入输出）、**集成**（通过 MCP Client 走真实协议）、**端到端**（在真实 Host 里让模型调用）。

端到端的测试要点：**模型会不会"自然地"选择调用你的工具**——这是 MCP Server 的真实使用场景。
